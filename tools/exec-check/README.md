# exec-check

テストが本番と同じ組み立てを通り、ソースが実際に実行されたかを検査する。入口からは `harness lint entry` と `harness lint coverage`。

テストが通っていても、次のどちらかが起きていると、仕様どおりに動くことの裏付けにならない。

- テストが、本番とは別の組み立てを通っている（テストの入口が経路や依存を自分で組み直している）。本番にだけある経路や、エラーの扱いが、テストから外れる。
- どのテストからも実行されないコードが残っている。

注釈（コードに書く名乗り）は、書けば通る。このツールは、ファイルの中身と、テストが書き出した実行の記録で確かめる。ファイルと記録を読むだけで、テストは実行しない。

## 設定（`harness.config.json`）

```json
{
  "entry": {
    "compose": "apps/api/src/node/deps.ts#assembleApps",
    "test_entry": "tests/support/app.ts#createTestApp"
  },
  "coverage": {
    "report": "coverage/lcov.info",
    "scope": ["apps/api/src", "packages/shared/src"],
    "not_run": [
      { "path": "apps/api/src/server.ts", "reason": "プロセスの入口。待ち受けはシナリオテストで確かめる" }
    ]
  }
}
```

| キー | 書くもの |
| --- | --- |
| `entry.compose` | 本番の組み立て。`<ファイル>#<名前>` |
| `entry.test_entry` | テストの入口。`<ファイル>#<名前>` |
| `coverage.report` | 実行の記録のファイル（lcov 形式）。テストのコマンド（`commands.test`）が毎回書き出す |
| `coverage.scope` | この記録で確かめるソースの範囲（パスか glob。`!` で除外）。省略すると `source.dirs` の全部 |
| `coverage.not_run` | どのテストからも実行されないことを認めたファイルと、その理由 |

- `entry` と `coverage` は、`{ "none": "<理由>" }` とも書ける。省略したものは「未宣言」と表示する。どちらも違反にはしないが、確かめていないことを毎回表示する。
- 確かめるソースは、設定の `source.dirs`（glob）と `source.extensions` に入るファイル。
- `coverage.scope` の外のソースは確かめず、件数を毎回表示する。画面のコードのように、別の種類のテストで確かめるものを外すのに使う。

## 検査項目

| ID | 内容 |
| --- | --- |
| X1 | `entry.compose` と `entry.test_entry` は `<ファイル>#<名前>` の形で、ファイルがプロジェクトの中に実在し、その中に名前が現れる |
| X2 | `entry.test_entry` のファイルの中に、`entry.compose` の名前が現れる（テストの入口が、本番の組み立てを呼んでいる）。2 つは別のファイル |
| V1 | 実行の記録が実在し、lcov として読めて、`--since` より新しい |
| V2 | 範囲に入るソースのファイルが、すべて記録に載っている |
| V3 | 実行する行を持つソースのファイルは、1 行以上実行されている（`not_run` に書いたファイルを除く） |
| V4 | `not_run` の各項目は、`path` が範囲に入るソースのファイルで、`reason` があり、実際に 1 行も実行されていない。実行されるようになったら違反になるので、項目を消す |
| V5 | `entry.compose` のファイルが実行されている（`entry` を宣言しているとき） |

確かめるのは、ここまでである。次のことは確かめない。

- X2 は、名前がファイルの中に現れるかを文字で見るだけである。呼んでいるか、コメントに書いてあるだけかは区別しない。実際に通っていることは、V5（本番の組み立てのファイルが実行されている）で確かめる。
- 仕様のテストが、テストの入口を通らずに本番のコードを直接読み込んでいないか。プロジェクトの lint の規則で止める（設定の `rules` に書く）。
- 行ごと・分岐ごとの実行。1 行でも実行されたファイルは通る。割合のしきい値は持たない。
- 実行された行が、正しい結果を確かめるテストから実行されたか。実行されたことと、確かめられたことは別である。
- 実行する行の無いファイル（型の宣言だけのファイルなど）。記録に載っていれば通る。

## 実行の記録の作り方

記録は lcov 形式（`SF:` / `DA:` / `end_of_record`）で、利用プロジェクトのテストのコマンドが書き出す。範囲に入るソースを、1 行も実行されなかったファイルも含めて、すべて記録に載せる設定にする（載っていないファイルは V2 の違反になる）。

完了の判定（`harness verify`。`tools/gate-hook/suite.mjs`）は、`commands.test` が通った直後に `lint coverage` を実行し、記録が `commands.test` を始めた時刻より新しいことを確かめる（`--since`）。前回の記録が残っているだけでは通らない。

## 使い方

```bash
node tools/exec-check/exec-check.mjs entry    [--root <プロジェクトのルート>] [--config <設定ファイル>]
node tools/exec-check/exec-check.mjs coverage [--root <プロジェクトのルート>] [--config <設定ファイル>] [--since <エポックからのミリ秒>]
```

終了コード: 0 = 違反なし（未宣言と none を含む） / 1 = 違反あり / 2 = 使い方の誤り、設定ファイルが無い、JSON として読めない。

## テスト

```bash
node --test tools/exec-check/test/*.test.mjs < /dev/null
```
