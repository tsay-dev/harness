# exec-check

テストが本番と同じ組み立てを通り、ソースが実際に実行され、アプリの入口が契約と合っているかを検査する。入口からは `harness lint entry`・`harness lint coverage`・`harness lint entries`。

仕様と実装の対応は、実装のコードに書く印（注釈）では確かめない（ADR-0070）。印は、書けば通り、消し忘れても通る。このツールは、テストが書き出した実行の記録と、アプリ自身が出した入口の一覧で確かめる。

テストが通っていても、次のどれかが起きていると、仕様どおりに動くことの裏付けにならない。

- テストが、本番とは別の組み立てを通っている（テストの入口が経路や依存を自分で組み直している）。本番にだけある経路や、エラーの扱いが、テストから外れる。
- どのテストからも実行されないコードが残っている（撤回した要件のために書いたコードが、テストを消した後も残っている、など）。
- 契約に無い入口がアプリに残っている。または、契約の操作に合う入口がアプリに無い。

このツールは、ファイルと記録を読むだけで、テストもコマンドも実行しない。実行の記録は `commands.test` が、入口の一覧は `commands.list_entries` が作る。完了の判定（`harness verify`。`tools/gate-hook/suite.mjs`）が、その 2 つを実行して、このツールに渡す。

## 設定（`harness.config.json`）

```json
{
  "entry": {
    "compose": "apps/api/src/node/deps.ts#assembleApps",
    "test_entry": "tests/support/app.ts#createTestApp"
  },
  "coverage": {
    "report": "coverage/lcov.info",
    "scope": ["apps/api/src", "packages/shared/src"],
    "not_run": [
      { "path": "apps/api/src/server.ts", "reason": "プロセスの入口。待ち受けはシナリオテストで確かめる" },
      { "path": "apps/api/src/jobs/cleanup.ts#purgeAll", "reason": "障害のときに手で呼ぶ処理。手順書で確かめる" }
    ]
  },
  "commands": {
    "list_entries": "node scripts/list-entries.mjs"
  },
  "entries": {
    "outside_contract": [
      { "entry": "GET /api/health", "reason": "監視が呼ぶ生存確認。利用者に見せる境界ではない" }
    ]
  }
}
```

| キー | 書くもの |
| --- | --- |
| `entry.compose` | 本番の組み立て。`<ファイル>#<名前>` |
| `entry.test_entry` | テストの入口。`<ファイル>#<名前>` |
| `coverage.report` | 実行の記録のファイル（lcov 形式）。テストのコマンド（`commands.test`）が毎回書き出す |
| `coverage.scope` | この記録で確かめるソースの範囲（パスか glob。`!` で除外）。省略すると `source.dirs` の全部 |
| `coverage.not_run` | どのテストからも実行されないことを認めたファイル（`<ファイル>`）と関数（`<ファイル>#<関数の名前>`）と、その理由 |
| `coverage.functions` | 関数の単位の検査（V6・V7）を使わないときにだけ、`{ "none": "<理由>" }` と書く。省略すると使う |
| `commands.list_entries` | アプリの入口の一覧を、標準出力へ 1 行 1 件の JSON で出すコマンド。コマンドか `{ "none": "<理由>" }` を必ず書く |
| `entries.outside_contract` | 契約に書かないことを認めた入口と、その理由（`{ "entry", "reason" }` の配列。省略できる） |

- `entry` と `coverage` は、`{ "none": "<理由>" }` とも書ける。省略したものは「未宣言」と表示する。どちらも違反にはしないが、確かめていないことを毎回表示する。
- `commands.list_entries` は省略できない（E4）。none が通るのは、撤回されていない契約に inbound の操作が 1 つも無い間だけ。
- 確かめるソースは、設定の `source.dirs`（glob）と `source.extensions` に入るファイル。
- `coverage.scope` の外のソースは確かめず、件数を毎回表示する。画面のコードのように、別の種類のテストで確かめるものを外すのに使う。

## 検査項目

| ID | 内容 |
| --- | --- |
| X1 | `entry.compose` と `entry.test_entry` は `<ファイル>#<名前>` の形で、ファイルがプロジェクトの中に実在し、その中に名前が現れる。名前は識別子 1 つ（`.` や `::` でつないだ名前は書けない） |
| X2 | `entry.test_entry` のファイルの中に、`entry.compose` の名前が現れる（テストの入口が、本番の組み立てを呼んでいる）。2 つは別のファイル |
| V1 | 実行の記録が実在し、lcov として読めて、`--since` より新しい |
| V2 | 範囲に入るソースのファイルが、すべて記録に載っている（`not_run` に書いたファイルは、載っていなくてもよい） |
| V3 | 実行する行を持つソースのファイルは、1 行以上実行されている（`not_run` に書いたファイルを除く） |
| V4 | `not_run` の各項目は、`path` が範囲に入るソースのファイルか `<ファイル>#<関数の名前>` で、`reason` があり、実際に 1 行も実行されていない（関数なら 1 回も呼ばれていない）。実行されるようになったら違反になるので、項目を消す。記録に無い名前の関数、ファイルごと認めたものの中の関数、同じ項目の重複も違反 |
| V5 | `entry.compose` のファイルが実行されている（`entry` を宣言しているとき）。記録に関数ごとの情報があれば、`compose` の名前の関数が 1 回以上呼ばれていることまで確かめる |
| V6 | 範囲に入るソースの、名前のある関数は、1 回以上呼ばれている（`not_run` に書いた関数を除く） |
| V7 | 記録に、関数ごとの情報（`FN:` / `FNDA:`）がある。出さない道具を使うなら、`coverage.functions` を `{ "none": "<理由>" }` にする |
| E1 | 一覧にある入口が、撤回されていない契約の inbound の操作のどれにも合わず、`entries.outside_contract` にも無い（契約に無い入口） |
| E2 | fixed の契約の、owned かつ inbound の操作に合う入口が、一覧に無い |
| E3 | `entries.outside_contract` の項目の形が誤っている（理由が無い、`entry` を読めない、重複）、一覧のどの入口にも合わない（古い宣言）、または契約にある入口を指している |
| E4 | 一覧を読めない: `commands.list_entries` が未宣言、none にできないのに none、JSON でない行、項目の欠落、知らない項目、同じ入口の重複 |

## 実行の記録の検査（coverage）

記録は lcov 形式（`SF:` / `DA:` / `FN:` / `FNDA:` / `end_of_record`。行ごとの `DA:` が無ければ、行の数の要約 `LF:` / `LH:` を読む）で、利用プロジェクトのテストのコマンドが書き出す。`SF:` のパスは、絶対パスか、プロジェクトのルート（monorepo では unit のディレクトリ）からの相対パスにする。git の最上位からの相対パスも受ける。記録のファイルは `.gitignore` に入れる（追跡されていないと、Stop フックが毎回「変更あり」と見て検査をやり直す）。範囲に入るソースを、1 行も実行されなかったファイルも含めて、すべて記録に載せる設定にする（載っていないファイルは V2 の違反になる）。

完了の判定は、`commands.test` が通った直後に `lint coverage` を実行し、記録が `commands.test` を始めた時刻より新しいことを確かめる（`--since`）。前回の記録が残っているだけでは通らない（ファイルの時刻の粒度のため、2 秒の幅は見逃す）。`commands.test` を実行しなかったとき（none、失敗、level が `lint`）は、`lint coverage` も実行しない。

### 関数の単位（V6・V7）

ファイルの単位だけでは、ほかの関数が使われているファイルの中の、どこからも呼ばれない関数を見逃す。撤回した要件のテストと入口を消した後に残る処理は、この形で残ることが多い。そこで、記録の `FN:` / `FNDA:` を読み、1 回も呼ばれなかった関数を違反にする。

- **認める書き方**: 呼ばれないことを認める関数は、`coverage.not_run` に `{ "path": "<ファイル>#<関数の名前>", "reason": "<理由>" }` と書く。名前は、記録の `FN:` に出ている名前をそのまま書く。認めた関数が呼ばれるようになったら V4 の違反になるので、項目を消す。
- **名前の無い関数は対象にしない**: 記録の名前が `(` か `<` で始まる関数と、`anonymous_<数字>` の形の関数（Istanbul の `(anonymous_3)`、Node の `anonymous_3` のような、道具が付けた仮の名前。無名のコールバックなど）は、数えない。仮の名前は編集のたびに変わるので、認める項目として指せないため。無名の関数の中だけにある処理は、関数の単位では見えない（行が 1 行も実行されないファイルなら、V3 が見つける）。道具によっては、変数に入れた関数式にも名前を付けない。
- **同じ名前の関数が 1 つのファイルに複数あるとき**: 記録は名前でしか区別できないので、呼ばれた回数を足して数える。どれか 1 つが呼ばれていれば通る。
- **1 行も実行されなかったファイルの関数**: V3 がファイルとして報告するので、関数ごとには重ねて報告しない。ファイルごと `not_run` に書いたものの中の関数も数えない。
- **関数ごとの情報を出さない道具**: 記録に `FN:` / `FNDA:` が 1 つも無ければ V7 の違反にする（関数の単位まで確かめたことにしない）。出せない道具を使うなら、`"functions": { "none": "<理由>" }` と書く。その間は、ファイルの単位までしか確かめていないことを毎回表示する。
- 割合のしきい値は持たない。

## 入口の一覧の検査（entries）

「契約に無い入口」は、コードの注釈では見つからない（注釈の無い入口は、注釈を探す検査から見えない）。そこで、アプリに入口の一覧を出させて、契約と突き合わせる。

### 一覧の形

`commands.list_entries` のコマンドは、標準出力へ、1 行に 1 件の JSON を出す。標準エラーの出力は読まない（読み込みの記録などは標準エラーへ出す）。空の行は読み飛ばす。

```jsonl
{"kind":"http","method":"GET","path":"/api/members/:accountId"}
{"kind":"http","method":"POST","path":"/api/members"}
{"kind":"push","name":"order.updated"}
{"kind":"deeplink","name":"myapp://item/{itemId}"}
```

| `kind` | 持つ項目 | 契約のどこと突き合わせるか |
| --- | --- | --- |
| `http` | `method`（`GET` などの 1 語）、`path`（`/` で始まる、接頭辞を含めた完全なパス） | `transport: http` の操作の `wire.method` と `wire.path` |
| `deeplink` / `push` / `stream` | `name` | その transport の操作の `entry` |
| `sdk` / `local-store` / `device` / `internal` | `name` | その transport の操作の名前（これらは契約に `entry` を持たない） |

- **本番と同じ組み立てから列挙する。** ルーターの登録を自分で書き写した一覧では、載せ忘れた入口が見つからない。本番の組み立て（`entry.compose`）で作ったアプリから、登録済みの経路を取り出して出す。
- **パスの突き合わせ**: `?`・`#` 以降と末尾の `/` を除き、パラメーターの書き方（`:name`、`:name{正規表現}`、`:name?`、`{name}`、`[name]`、`${…}`、`*`）を同じものとみなす。パラメーターの名前は比べない。そのうえで、区切りごとに完全に一致するかを見る（前方一致・後方一致はしない）。method は、大文字と小文字を区別せずに比べる。deeplink の `name` も、パラメーターの書き方を同じにならす。
- すべての method を受ける登録（`all` など）は、受ける method ごとに 1 行ずつ出す。
- 上の項目のほかの項目を持つ行、同じ入口を 2 回出す一覧は、E4 の違反にする。

### 契約のどの操作を数えるか

- **E1**（一覧 → 契約）: 撤回されていない UC の契約の、`direction: inbound` の操作。契約が draft でも、owned が false でも、合えば通る。outbound の操作（外の API を呼ぶ側）と同じパスの入口は、契約にある入口とは数えない。
- **E2**（契約 → 一覧）: 撤回されていない UC の、`x-status: fixed` の契約の、`owned: true` かつ `direction: inbound` の操作。draft の契約の操作は、まだ入口を求めない。
- **none**: `commands.list_entries` を `{ "none": "<理由>" }` にできるのは、撤回されていない契約に inbound の操作が 1 つも無い間だけ。

### 契約に書かない入口

生存確認のように、契約に書かないと決めた入口は、`entries.outside_contract` に理由と一緒に書く。`entry` は、http なら `"GET /api/health"`（method とパス）、それ以外なら `"deeplink myapp://open"`（種類と名前）の形。入口が無くなったら項目も消す（残っていれば E3）。契約にある入口を書いても E3 になる。

### 単独で呼ぶ

```bash
node scripts/list-entries.mjs | harness lint entries          # 標準入力から
harness lint entries --from /tmp/entries.jsonl                # ファイルから
```

`commands.list_entries` が none・未宣言のときは、一覧を渡さなくても判定する。`harness lint`（まとめて実行）には入らない（一覧が要るので、引数なしでは意味が決まらない）。完了の判定は、level `fast` 以上で `commands.list_entries` を unit のディレクトリで実行し、標準出力を一時ファイルに書いて渡す。level `lint` では、コマンドを実行しないので skip として表示する（none・未宣言の判定は、level `lint` でも行う）。

## 確かめないこと

- X2 は、名前がファイルの中に現れるかを文字で見るだけである。呼んでいるか、コメントに書いてあるだけかは区別しない。逆に、テストの入口が別のファイルを経由して本番の組み立てを呼ぶ形は、名前が現れないので違反になる。テストの入口のファイルから、名前で直接呼ぶ形にする。
- 実際に呼ばれたことは、V5 で確かめる。記録に関数ごとの情報があれば、組み立ての関数が呼ばれた回数を見る。無ければ、確かめられるのは「組み立てのファイルが読み込まれた」ことまでである（ファイルは、読み込むだけで一部の行が実行済みになる）。
- 仕様のテストが、テストの入口を通らずに本番のコードを直接読み込んでいないか。プロジェクトの lint の規則で止める（設定の `rules` に書く）。
- 行ごと・分岐ごとの実行。1 回でも呼ばれた関数は通る。まだ呼ばれている関数の中に、枝として残っている処理（撤回した要件のための分岐など）は見つからない。
- 実行された行が、正しい結果を確かめるテストから実行されたか。実行されたことと、確かめられたことは別である。
- 実行する行の無いファイル（型の宣言だけのファイルなど）。記録に載っていれば通る。
- 一覧に載っていない入口。一覧は利用プロジェクトのコマンドが出すので、コマンドが載せ忘れた入口は見つからない。
- 入口の先の処理が、契約の形（リクエスト、レスポンス、エラー）どおりに動くか。それは契約の実例の実行（`harness run cases`）が確かめる。

## 使い方

```bash
node tools/exec-check/exec-check.mjs entry    [--root <プロジェクトのルート>] [--config <設定ファイル>]
node tools/exec-check/exec-check.mjs coverage [--root <プロジェクトのルート>] [--config <設定ファイル>] [--since <エポックからのミリ秒>]
node tools/exec-check/exec-check.mjs entries  [--root <プロジェクトのルート>] [--config <設定ファイル>] [--from <入口の一覧のファイル>]
```

終了コード: 0 = 違反なし（未宣言と none を含む） / 1 = 違反あり / 2 = 使い方の誤り、設定ファイルが無い、JSON として読めない、`--from` のファイルが無い。

## テスト

```bash
node --test tools/exec-check/test/*.test.mjs < /dev/null
```
