# lint entry

テストの入口が、本番と同じ組み立てを呼んでいるかを検査する（`harness lint entry`）。

テストが通っていても、テストが本番とは別の組み立てを通っている（テストの入口が経路や依存を自分で組み直している）と、本番にだけある経路や、エラーの扱いが、テストから外れる。仕様どおりに動くことの裏付けにならない。

仕様と実装の対応を、実装のコードに書く印ではなく実行で確かめる考え方（ADR-0070）と、3 つの検査（`lint entry`・`lint coverage`・`lint entries`）の分担は、`../lint-coverage/README.md` に書く。このコマンドは、ファイルを読むだけで、テストもコマンドも実行しない。

## 設定（`harness.config.json`）

```json
{
  "entry": {
    "compose": "apps/api/src/node/deps.ts#assembleApps",
    "test_entry": "tests/support/app.ts#createTestApp"
  }
}
```

| キー | 書くもの |
| --- | --- |
| `entry.compose` | 本番の組み立て。`<ファイル>#<名前>` |
| `entry.test_entry` | テストの入口。`<ファイル>#<名前>` |

- `entry` は、`{ "none": "<理由>" }` とも書ける。省略すると「未宣言」と表示する。どちらも違反にはせず、確かめていないことを毎回表示する。
- `entry` は義務にしていない（本番の組み立てとテストの入口が分かれないスタックがある）。

## 検査項目

| ID | 内容 |
| --- | --- |
| X1 | `entry.compose` と `entry.test_entry` は `<ファイル>#<名前>` の形で、ファイルがプロジェクトの中に実在し、その中に名前が現れる。名前は識別子 1 つ（`.` や `::` でつないだ名前は書けない） |
| X2 | `entry.test_entry` のファイルの中に、`entry.compose` の名前が現れる（テストの入口が、本番の組み立てを呼んでいる）。2 つは別のファイル |

本番の組み立てが実際に実行されたかは、実行の記録で確かめる（`harness lint coverage` の V5。`../lint-coverage/README.md`）。

## 確かめないこと

- X2 は、名前がファイルの中に現れるかを文字で見るだけである。呼んでいるか、コメントに書いてあるだけかは区別しない。逆に、テストの入口が別のファイルを経由して本番の組み立てを呼ぶ形は、名前が現れないので違反になる。テストの入口のファイルから、名前で直接呼ぶ形にする。
- 実際に呼ばれたことは、V5 で確かめる。記録に関数ごとの情報があれば、組み立ての関数が呼ばれた回数を見る。無ければ、確かめられるのは「組み立てのファイルが読み込まれた」ことまでである（ファイルは、読み込むだけで一部の行が実行済みになる）。
- 仕様のテストが、テストの入口を通らずに本番のコードを直接読み込んでいないか。プロジェクトの lint の規則で止める（設定の `rules` に書く）。

## 使い方

```bash
harness lint entry [--root <プロジェクトのルート>] [--config <設定ファイル>]
```

終了コード: 0 = 違反なし（未宣言と none を含む） / 1 = 違反あり / 2 = 使い方の誤り、設定ファイルが無い、JSON として読めない。

## テスト

```bash
node --test tools/lint-entry/test/*.test.mjs < /dev/null
```
