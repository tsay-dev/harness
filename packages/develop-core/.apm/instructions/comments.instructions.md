# 💬 コード内コメントには現在の仕様だけを書く

> 対象はすべてのプラットフォームの本番コードとテストコードです。フレームワーク固有の記法（doc comment の形式）は各フレームワークの coding 末端ファイルが上書きし、この文書は書く内容と書かない内容だけを定めます。新しいフレームワークを追加したら、その言語の拡張子を上記 `applyTo:` に追加します。コメントは日本語で書き、識別子、API 名、フレームワークのキーワードは維持します。

## 到達状態

コメントは、今このコードを読む人が**現在の仕様**を理解するためだけに存在します。履歴は git コミットメッセージと ADR にあり、コードに複製すると更新されない 2 つ目の記録になります。

- **書かないもの（見つけたら触った範囲で削除する）**: 過去との差分（「以前は X だったが Y に変更した」）、作業記録や日付・担当者・チケット番号だけの注記、コメントアウトした古いコード、変更の意図（コミットメッセージ / ADR へ）、コードの言い換え。
- **書いてよいもの**: 読むだけでは分からない理由と制約（外部仕様の癖、意図的に非効率な選択、回避しているバグ）、壊れやすい前提と不変条件、フレームワークが要求する doc comment。すべて現在形で書きます。
- 履歴コメントが現在の仕様の説明も兼ねていたら、先に現在形へ書き直してから履歴部分を落とします。正しいか確認できないコメントはコードを正として判断し、コメントを根拠に実装を変えません。清掃は同じコミットの一部として扱い、報告に 1 行残します。

## トレーサビリティ注釈（ID のみ）

`trace-check`（`"${HARNESS_ROOT}/tools/trace-check/"`）が読む、必ず入れる唯一のコメントです。要件を言い換えず ID だけを書きます（R-701。存在しない ID は C5）。

- **本番コード**: 実現単位（ユースケースクラス、ルール関数、検査を強制する分岐）の doc comment に `@implements REQ-nnn` / `@implements BR-nnn` / `@implements UC-nnn`。複数 ID は `,` または `/` で区切って 1 行に書けます（`/// @implements UC-001, REQ-009 / BR-015`）。ファイルヘッダーではなく単位に置きます（C14 は存在を要求し、粒度はこの文書が定めます）。
- **テストコード**: テストごとに `@covers REQ-nnn#class` を宣言済みクラスにちょうど 1 つ。位置は利用プロジェクトが `traceconfig.json` の `tests.covers_placement` に宣言し（`before` = テスト直上の doc comment、`after` = 本体の先頭行）、C10 / C11 が検査します。
- **スキーマ正本**（migration、`schema.prisma`、モデルファイル）: ルールを強制する制約に、その書式のコメント構文で `@implements BR-nnn`（`-- @implements BR-007`）。C13 と C14 が読みます。
- 注釈は現在の仕様の参照先です。要件の撤回や移動と同じ変更で更新・削除します。
