仕様・コード・検査はどう紐づいているか

手書きの図（docs → codes → checks）と同じ並びで、harness の現在の実装をそのまま描いています。根拠は docs.instructions.md の R- 規則、templates/develop/、tools/ の各検査ツールのコードです。

  • docs は GOAL → UC → REQ と BR に加えて、UC ごとの contract.yaml と共有語彙 components.yaml があり、これがコードとの 2 つ目の接点になっています。
  • code には本番コードとテストの 2 種類があります。手で書く紐づきはテストの側だけで（ADR-0070）、テストが注釈（@covers / @scenario）で仕様の ID を指します。注釈として数えるのはコメントの中にあるものだけで、どのテストの注釈かはテストの印の直上（または直後）のコメント行の「窓」で決まります。本番コードには紐づきの印を書かず、実装との対応は、テストの実行の記録と、アプリが出す入口の一覧で確かめます（exec-check）。
  • checks は 2 つではなく 3 層です。文書と注釈を読む静的検査（spec-lint、trace-check）、実際に動かす検査と、動かした記録を読む検査（contract-run、テスト、exec-check）、書き込み・終了・コミットで止める関所（gate-hook、stop-gate、spec-lint gate、git-lint）です。
  • 点線の紐づけは機械が検査せず、reviewer が担う線です。どの線にも、機械が見るのは注釈や参照の存在までで、意味の正しさは人間ゲートと reviewer が担います。
  • 紐づきに例外はありません（ADR-0056）。baseline も、コードに書く例外の印もありません。対象が本当に無い範囲だけを harness.config.json に理由付きの none で宣言し、active な文書が求める範囲は none にできません（義務表、C26）。
文書同士の参照（機械が検査） コードの注釈・実行（機械が検査） 機械が検査しない線 矢印の向き = 参照を書く側 → 参照される側

3. 検査がかかるタイミング

同じ検査でも、誰がいつ実行するかで役割が違います。gate-hook と stop-gate は利用プロジェクトが明示的に有効にしたときだけ動き、無効ならオーケストレーターが同じ条件を自分で守ります。

1 · 仕様を書いた直後

作成者の自己検査

  • ID 採番は trace-check --next
  • spec-lint validate
  • trace-check --as-active --only …（承認後に出る違反を先に見る）

その後、人間が承認して active にする。UC の active と契約の fixed は gate-hook が承認を求める。

2 · 実装を書く直前

gate-hook（PreToolUse）

  • UC が active
  • REQ に draft がない
  • 契約が fixed
  • UC の phase が 実装 / 検証

満たさなければ書き込みを止める。harness.config.json・検査器・hook の設定・workflow・status の降格は人間に承認を求める（ask）。

3 · ターン終了時

stop-gate（Stop）

  • spec-lint → trace-check → contract-run
  • typecheck → lint → test
  • system（シナリオテスト）

コマンドは harness.config.json の commands だけから取る（4 キーは宣言か none が必須）。harness.config.json が無ければ失敗。例外でも止める（fail-closed）。

4 · コミット時

spec-lint gate

  • UC: trailer の UC と REQ が active
  • 契約が fixed

commit-msg hook への接続は任意。

5 · PR / CI

git-lint ほか

  • ブランチ名 B1–B3
  • コミットヘッダー M1–M3
  • spec-lint・trace-check（harness_ref で固定した版。unit ごと）
  • harness.config.json・status・workflow の変更をジョブ要約に出す

git 未宣言なら「未検査」。merge で止めるのはブランチ保護と CODEOWNERS。

6 · スライス完了

判定と人間ゲート

  • reviewer の「阻止」がゼロ
  • reviewer の「問い」に人間が答え済み
  • UC の phase が 完了

テストが全部通っただけでは完了ではない。

義務表（C26）: none にできない範囲

active な文書と fixed な契約が「義務」を生みます。義務が無い間は none も空の範囲も通るので、新規プロジェクトの最初のターンと移行の途中は止まりません。文書を active にした時点で、対応する宣言が必要になります。

active な UCdocs.glossary
fixed 契約の inbound の操作source（owned かつ inbound）。入口の一覧 commands.list_entries を none にできないことは、exec-check の E4 が見る

義務がある範囲で、テストの印の一致が 0 件なのも違反です。宣言した固定パスが無いことは、active な UC があれば違反（作るか、理由付きの none にする）、それ以外はレポートに「未作成」と出すだけです。

5. 機械が見ていないもの

点線の線と、注釈の「意味」は機械では検査していません。担い手ごとに分けると次の通りです。

人間ゲート

仕様の内容が正しいか（docs の承認で active・frozen・living にする）、UI の見た目（目視）、DB スキーマ。

reviewer（別コンテキスト）

実行されたコードが本当に要件を実現しているか、テストの assertion が EARS 文の意味を検証しているか、@covers BR-nnn のテストが入口を通さず DB に直接入れているか、分割クラスが入力空間を尽くすか、ロケーターが用語集と契約から導かれているか。

reviewer（別コンテキスト）

どの規則も説明しない制約がスキーマに無いか（機械はスキーマの制約を読まない）。coverage.not_run の理由が妥当か。none の宣言を含む harness.config.json の変更は人間が承認する（gate-hook が確認を求める）。

reviewer（別コンテキスト）

NFR のテストや measured_by の計測が、閾値を本当に測っているか。C20 が見るのは、検証の所在が docs の外のファイルとして実在し、中に NFR の ID が現れることまで。外部の計測は runbook に ID と計測先を書く。

補足

contract-run が確かめるのは応答の形とエラーコードまで。その背後の要件が満たされているかは、各 REQ に宣言したテストが担う。

主張の外

テストが実際に実行されたこと。trace-check は紐づきの有無を見るだけで、@covers したテストが CI で走って通ったかは突き合わせない（ADR-0056 の M9）。実行の記録が示すのは、どのコードがどれかのテストから実行されたかまでで、どの要件のテストから実行されたかは示さない。

主張の外

撤回した要件のためのコードが、まだ呼ばれている関数の中の枝として残ること。名前の無い関数（無名のコールバック）の中だけにある処理。入口の一覧を出すコマンドが載せ忘れた入口。コードを読んだその場では、どの要件のためのコードかは分からない（harness index で要件のテストを引き、そのテストが実行するコードを見る）。

ブランチ保護

Bash や Claude Code 以外のプロバイダーでの harness.config.json と status の変更は、gate-hook の承認を通らない。harness.config.json・docs/・.github/workflows/ を CODEOWNERS とブランチ保護で必須レビューにしない限り、機械では止まらない。monorepo の unit の docs の status も ask しない。
