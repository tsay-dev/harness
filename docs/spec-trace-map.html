仕様・コード・検査はどう紐づいているか

手書きの図（docs → codes → checks）と同じ並びで、harness の現在の実装をそのまま描いています。根拠は docs.instructions.md の R- 規則、templates/develop/、tools/ の各検査ツールのコードです。

  • docs は GOAL → UC → REQ と BR に加えて、UC ごとの contract.yaml と共有語彙 components.yaml があり、これがコードとの 2 つ目の接点になっています。
  • code には本番コードとテストの 2 種類があり、どちらも注釈（@implements / @covers / @scenario）で仕様の ID を指します。
  • checks は 2 つではなく 3 層です。文書と注釈を読む静的検査（spec-lint、trace-check）、実際に動かす検査（contract-run、テスト）、書き込み・終了・コミットで止める関所（gate-hook、stop-gate、spec-lint gate、git-lint）です。
  • 点線の紐づけは機械が検査せず、reviewer が担う線です。どの線にも、機械が見るのは注釈や参照の存在までで、意味の正しさは人間ゲートと reviewer が担います。
文書同士の参照（機械が検査） コードの注釈・実行（機械が検査） 機械が検査しない線 矢印の向き = 参照を書く側 → 参照される側

3. 検査がかかるタイミング

同じ検査でも、誰がいつ実行するかで役割が違います。gate-hook と stop-gate は利用プロジェクトが明示的に有効にしたときだけ動き、無効ならオーケストレーターが同じ条件を自分で守ります。

1 · 仕様を書いた直後

作成者の自己検査

  • ID 採番は trace-check --next
  • spec-lint validate
  • trace-check --only C4,C9,C12

その後、人間が承認して active にする。

2 · 実装を書く直前

gate-hook（PreToolUse）

  • UC が active
  • REQ に draft がない
  • 契約が fixed
  • UC の phase が 実装 / 検証

満たさなければ書き込みを止める。

3 · ターン終了時

stop-gate（Stop）

  • spec-lint → trace-check → contract-run
  • typecheck → lint → test
  • system（シナリオテスト）

コマンドは traceconfig.json の commands だけから取る。

4 · コミット時

spec-lint gate

  • UC: trailer の UC と REQ が active
  • 契約が fixed

commit-msg hook への接続は任意。

5 · PR / CI

git-lint ほか

  • ブランチ名 B1–B3
  • コミットヘッダー M1–M3
  • trace-check、テスト

git 未宣言なら「未検査」。

6 · スライス完了

判定と人間ゲート

  • reviewer の「阻止」がゼロ
  • 持ち越しは DEFERRED.md へ
  • UC の phase が 完了

テストが全部通っただけでは完了ではない。

5. 機械が見ていないもの

点線の線と、注釈の「意味」は機械では検査していません。担い手ごとに分けると次の通りです。

人間ゲート

仕様の内容が正しいか（docs の承認で active・frozen・living にする）、UI の見た目（目視）、DB スキーマ。

reviewer（別コンテキスト）

注釈した単位が本当に要件を実現しているか、テストの assertion が EARS 文の意味を検証しているか、分割クラスが入力空間を尽くすか、ロケーターが用語集と契約から導かれているか。

reviewer（別コンテキスト）

「仕様外」の印が正当か（REQ にすべき振る舞いを技術部品として逃がしていないか）。source.unit_pattern を宣言していない利用プロジェクトでは、仕様を指さない本番コードは検査されない。

reviewer（別コンテキスト）

NFR のテストや measured_by の計測が、閾値を本当に測っているか。C20 が見るのは検証の所在があることと、パスが実在することまで。

補足

contract-run が確かめるのは応答の形とエラーコードまで。その背後の要件が満たされているかは、各 REQ に宣言したテストが担う。
