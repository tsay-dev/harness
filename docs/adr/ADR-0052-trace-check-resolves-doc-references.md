# ADR-0052 文書が参照する BR・REQ・アクター・KPI の実在と、UC の表と REQ の 1 対 1 を trace-check が検査する

## Context

仕様・コード・検査の紐づきを図にした（`docs/spec-trace-map.html`）ところ、文書同士の参照のうち、参照先が実在するかを機械が見ていない線が 3 本あった。

- **UC・REQ から BR への参照。** C4 は「どこからも参照されない BR」を検出する逆向きの検査で、UC や REQ の `br:` が指す BR が無くても通る。spec-lint が見るのは `br:` の書式だけ。
- **UC の状態 × イベント表のセルから REQ への対応。** spec-lint は空セルが無いことだけを見る。`--next req` は表の ID を予約済みと数えるだけなので、予約した REQ が作られなくても、別の UC の REQ を指していても、表に無い REQ があっても通る（R-404 は「対応は表だけが持つ」と定める）。
- **GOAL の `actor:`・`origin:` と UC の `actor:`。** spec-lint はキーがありプレースホルダーでないことだけを見る。trace-check の ID 空間は GOAL・UC・REQ・BR・NFR・ADR で、ACT と KPI は対象外。C15 は表に無いアクターを人間とみなすため、打ち間違えたアクターはエラーにならない。

R-101 は「事実は 1 か所にあり、ほかは ID で参照する」と定めるが、参照先の実在が保証されないと、SSOT の参照が切れたまま人間ゲートを通る。

## Decision

trace-check に 3 つの検査を足す。既存の C1–C15 の意味は変えない。

- **C16**: `active` な UC / REQ の本文（frontmatter の `br:` を含む）が参照する BR が定義されている。`withdrawn` の BR は定義済みと数える。
- **C17**: `active` な UC の表とその UC の REQ が 1 対 1 に対応する。表が未定義の REQ や別の UC の REQ を指す場合と、REQ（`withdrawn` を除く）が表のどのセルからも導出されていない場合が違反。UC 本文に REQ の一覧を置かない規律（R-404）があるので、本文に現れる REQ ID はすべて表のセルとして扱い、表の節を解析しない。
- **C18**: `active` な GOAL の `actor` / `origin` と、`active` な UC の `actor` が、`docs.actors` の表（`ACT-nn`）と `docs.vision` の KPI 表（先頭セルが `KPI-nn` の行）に定義されている。`traceconfig.json` に `docs.vision` を足し、テンプレートに既定値を置く。キーが未宣言ならその参照は判定しない（C13・C15 と同じ扱い）。
- 3 つとも `active` の文書だけを対象にする（C1・C8・C14・C15 と同じ）。HTML コメントの中の ID と、番号が 0 だけのプレースホルダー（spec-lint の担当）は数えない。
- 強制は trace-check で、develop の完了条件（新規違反ゼロ）、stop-gate、CI の spec-gate を通じて効く。

## Consequences

- 良: 承認済みの文書が、存在しない BR・REQ・アクター・KPI を指したまま完了判定を通らなくなる。
- 良: 表で予約したまま作られなかった REQ と、表を経ずに足された REQ が見つかる。
- 悪: 既存の利用プロジェクトでは、harness を上げると新規違反が出うる。R-804 に従い、検査を初めて当てる時点で `--update-baseline` を 1 回だけ使って既知にする。
- 悪: UC を承認してから REQ を作るまでの間、C17 が違反を出す。stop-gate を有効にしている利用プロジェクトでは、その間のターン終了が止まる（承認済み GOAL に UC が無い間の C8、承認済み REQ にテストが無い間の C1 と同じ性質）。
- 悪: 参照先が `withdrawn` かどうかは見ない。承認済みの文書が撤回済みの BR や REQ を指していても通る。
- 悪: `docs.vision` を宣言していない既存の利用プロジェクトでは、`origin` は判定されないまま。宣言を足すまで、この参照は未検査に残る。

## 却下した選択肢

- **spec-lint で検査する**: spec-lint はファイル単位の書式とライフサイクルの担当で、文書をまたぐ参照の解決は trace-check の担当。両方に参照解決を持たせると、形式検証を重複させないという境界が崩れる。
- **C4・C9 の意味を広げる**: 既存の番号の意味が変わると、利用プロジェクトの baseline のキーと `--only` の指定が別の検査を指すことになる。番号を足す。
- **UC の表の節だけを解析する**: 表の見出しと列の形に依存する。R-404 で UC 本文に REQ の一覧を置かないので、本文全体の REQ ID を表のセルとみなせば解析が要らない。
- **`withdrawn` の参照先も違反にする**: 撤回の扱い（参照側も撤回するか、置き換え先に張り替えるか）が決まっていない。実在の検査だけを先に入れる。
- **`docs.vision` を推測して既定のパスを読む**: trace-check は `traceconfig.json` の宣言だけからパスを取る。推測で読むと、宣言の無い利用プロジェクトで意図しない判定が走る。
