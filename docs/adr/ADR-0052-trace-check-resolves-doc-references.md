# ADR-0052 文書が参照する BR・REQ・アクター・KPI の実在と状態、UC の表と REQ の 1 対 1 を trace-check が検査する

## Context

仕様・コード・検査の紐づきを図にした（`docs/spec-trace-map.html`）ところ、文書同士の参照のうち、参照先が実在するかを機械が見ていない線が 3 本あった。

- **UC・REQ から BR への参照。** C4 は「どこからも参照されない BR」を検出する逆向きの検査で、UC や REQ の `br:` が指す BR が無くても通る。spec-lint が見るのは `br:` の書式だけ。
- **UC の状態 × イベント表のセルから REQ への対応。** spec-lint は空セルが無いことだけを見る。`--next req` は表の ID を予約済みと数えるだけなので、予約した REQ が作られなくても、別の UC の REQ を指していても、表に無い REQ があっても通る（R-404 は「対応は表だけが持つ」と定める）。
- **GOAL の `actor:`・`origin:` と UC の `actor:`。** spec-lint はキーがありプレースホルダーでないことだけを見る。trace-check の ID 空間は GOAL・UC・REQ・BR・NFR・ADR で、ACT と KPI は対象外。C15 は表に無いアクターを人間とみなすため、打ち間違えたアクターはエラーにならない。

R-101 は「事実は 1 か所にあり、ほかは ID で参照する」と定めるが、参照先の実在が保証されないと、SSOT の参照が切れたまま人間ゲートを通る。

最初の案（参照先の実在だけを見る、UC 本文の REQ ID をすべて表のセルとみなす）は、レビューで次の抜けと誤検知が見つかったので改めた。

- active な REQ が draft の BR を `br:` で参照でき、承認されていない規則に依存したまま実装が進む。撤回済みの BR を指していても通る。
- 主シナリオや事前条件の散文で他の UC の REQ に触れると、表のセルと数えられ「別の UC の REQ を指す」違反になる。
- active な UC の表のセルがすべて「不可」で、REQ が 1 件も無くても通る。

## Decision

trace-check に 3 つの検査を足す。既存の C1–C15 の意味は変えない。

- **C16**: `active` な UC / REQ の本文（frontmatter の `br:` を含む）が参照する BR は、定義されていて `active` であること。未定義、`draft`、`withdrawn` の BR を指すと違反（`draft` なら「BR を承認して active にするか、参照を外す」と案内する）。
- **C17**: `active` な UC の表とその UC の REQ が 1 対 1 に対応する。表とみなすのは見出しが「状態」「例外系」で始まる `##` の節だけ（spec-lint と同じ判定。「## 状態 × イベント表」「## 例外系の走査」）。表が未定義の REQ、別の UC の REQ、撤回済みの REQ を指す場合と、その UC の REQ（`withdrawn` を除く）が表のどのセルからも導出されていない場合が違反。`active` な UC は `active` か `draft` の REQ を 1 件以上持つ。
- **C18**: `active` な GOAL の `actor` / `origin` と、`active` な UC の `actor` が、`docs.actors` の表（`ACT-nn`）と `docs.vision` の KPI 表（先頭セルが `KPI-nn` の行）に定義されている。`traceconfig.json` の `docs.actors` / `docs.vision` は宣言が必須で、対象が無ければ理由付きの none にする。active な文書が `ACT-nn` / `KPI-nn` を持つ間は none にできない（C26。ADR-0056）。
- 対象は `active` の文書だけ（C1・C8・C14・C15 と同じ）。HTML コメントの中の ID と、番号が 0 だけのプレースホルダー（spec-lint の担当）は数えない。spec-author は承認前に `--as-active`（draft を active とみなす。ADR-0056）で、承認後に出る違反を先に見られる。
- 強制は trace-check で、develop の完了条件（違反ゼロ）、stop-gate、CI の spec-gate を通じて効く。

## Consequences

- 良: 承認済みの文書が、存在しない・未承認・撤回済みの BR、存在しない REQ・アクター・KPI を指したまま完了判定を通らなくなる。
- 良: 表で予約したまま作られなかった REQ、表を経ずに足された REQ、REQ を 1 件も持たない active な UC が見つかる。
- 良: 散文の中の他 UC の REQ への言及は表のセルと数えないので、参照を消すために本文を書き換える必要が無い。
- 悪: 既存の利用プロジェクトでは、harness を上げると違反が出うる。baseline は無い（ADR-0056）ので、参照を直すか、揃うまで文書を `draft` に戻す。
- 悪: UC を承認してから REQ を作るまでの間、C17 が違反を出す。stop-gate を有効にしている利用プロジェクトでは、その間のターン終了が止まる（承認済み GOAL に UC が無い間の C8、承認済み REQ にテストが無い間の C1 と同じ性質）。
- 悪: BR を先に承認しないと、それを参照する REQ を active にできない。承認の順序が 1 つ増える。
- 悪: C17 は節の見出しに依存する。見出しを変えた UC は表が空と読まれ、その UC の REQ がすべて「導出されていない」と報告される（黙って通るのではなく落ちる側に倒れる）。

## 却下した選択肢

- **spec-lint で検査する**: spec-lint はファイル単位の書式とライフサイクルの担当で、文書をまたぐ参照の解決は trace-check の担当。両方に参照解決を持たせると、形式検証を重複させないという境界が崩れる。
- **C4・C9 の意味を広げる**: 既存の番号の意味が変わると、`--only` の指定や過去の報告が別の検査を指すことになる。番号を足す。
- **UC 本文に現れる REQ ID をすべて表のセルとみなす**（最初の案）: 散文の中の他 UC の REQ への言及が違反になる。表の節はテンプレートの見出しで決まっているので、節を限っても解析は軽い。
- **参照先の実在だけを見て、`draft` / `withdrawn` の BR も定義済みと数える**（最初の案）: 承認されていない規則や撤回した規則に依存した要件が、承認済みとして実装に進む。
- **`docs.vision` / `docs.actors` を推測して既定のパスを読む**: trace-check は `traceconfig.json` の宣言だけからパスを取る。推測で読むと、宣言の無い利用プロジェクトで意図しない判定が走る。省略は設定エラーにして、不在は none で宣言させる（ADR-0056）。
