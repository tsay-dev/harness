# ADR-0051 利用プロジェクトの作業指針は地図だけを持ち、入口は命名規則で 1 回宣言し、行数を spec-lint が検査する

## Context

ある利用プロジェクト（Cloudflare / Hono / React のモノレポ）で、1 つのユニットの `CLAUDE.md` が 1,135 行（約 274KB）になった。そのディレクトリで作業する agent は、毎回これを丸ごと読み込む。中身は次のとおりで、大半は別の場所に正本がある事実の写しだった。

| 中身 | 行数の目安 |
| --- | --- |
| 操作ごとの入口・注入する依存・テスト用 app と境界フェイクの使い方 | 約 385 |
| REQ を持たない技術部品の仕様（DB の依存、外部境界のクライアント、環境変数の読み方など） | 約 325 |
| 画面の識別子・失敗の写し方の表 | 約 200 |
| 反映・シードなど人の運用手順 | 約 100 |

原因は harness の規約にある。

- test-author は実装を読まない。その代わりに、操作ごとの入口・注入する境界・fixture の提供元を「利用プロジェクトが宣言する」（`rules-cloudflare-hono-react` の「操作 → 入口」、R-1204）。宣言の置き場所として名前が出るのは `CLAUDE.md` / `AGENTS.md` だけで、実装を読まずにテストを書ける詳しさで書くため、宣言が実装のインターフェースの写しになる。
- test-author がテストの足場（`tests/` の境界フェイク、fixture、テスト用 app）を読んでよいかが書かれていない。使い方はすでにそのコードの型とコメントにあるのに、作業指針にもう一度書かれた。
- REQ は外から観測できる振る舞いだけを持つ（R-401）。外部境界のクライアントや設定の読み取りなど、REQ を持たない技術部品の振る舞いの置き場所が無く、作業指針に流れ込んだ。
- 1 ファイル 100 行の目安（R-1005）と写しの禁止（R-101）は `docs/**` にだけ効き、作業指針は機械の検査の外にある。

同じ規約で書かれた別のユニットは、テストと運用の説明を `TESTING.md`・`README.md` に分けて 51 行に収まっている。規約が置き場所を決めていないことが、利用プロジェクトごとの差になっている。

## Decision

- **作業指針は地図**（R-1010 を新設）。`docs/` と同じ階層の `CLAUDE.md` / `AGENTS.md` が持つのは、構成、層の向き、命名規則、`traceconfig.json` に置けない逸脱、正本へのリンクだけ。コード・設定・テストに正本がある事実と、人の運用手順（README へ）を写さない。`docs.instructions.md` の `applyTo` に `**/CLAUDE.md,**/AGENTS.md` を足し、作業指針を書く担当に届ける。
- **入口は命名規則で 1 回宣言する**（R-1204 を改訂）。操作ごとの表にせず、規則に従わないものだけを挙げる。`rules-cloudflare-hono-react` は既定の命名（機能 `<feature>` の操作は `apps/api/src/features/<feature>/<feature>.routes.ts` の `create<Feature>Routes` が受ける）を自ら持ち、利用プロジェクトが宣言するのは UC または操作 → 機能の対応、接頭辞、命名の例外だけにする。
- **テストの足場は test-author が読む**。`tests.dirs` 配下の境界フェイク、fixture、テスト用 app は実装ではないので読み、その型とコメントを使い方の正本にする（test-author の入力契約）。実装（`source`）を読まない独立性は変えない。
- **REQ を持たない技術部品の振る舞いの正本は、その単位の doc comment**。自己検査は implementer が書き、独立性を求めない（implementer の不変条件）。外から観測できる振る舞いは今までどおり REQ と test-author が持つ。
- **強制**: spec-lint `validate` が、`docs/` の親ディレクトリの `CLAUDE.md` / `AGENTS.md` が 150 行を超えたら err にする。メッセージに実際の行数を入れず、baseline のキーを編集のたびに動かさない。写しを入れていないかは reviewer の確認で、説得による統制（R-901）。

## Consequences

- 良: 機能を足しても作業指針がほとんど増えない。命名規則に従う入口は宣言が要らない。
- 良: フェイクと技術部品の説明の正本がコードの 1 か所になり、作業指針との食い違いが無くなる。
- 良: 作業指針の肥大を CI（spec-lint）が止める。
- 悪: 150 行を超える作業指針を持つ既存の利用プロジェクトは、harness を上げると spec-lint が落ちる。分割するか、移行中は `--update-baseline` で既知にする必要がある。baseline に載った作業指針は、それ以上膨らんでも新規の違反にならない（行数を見ないため）。
- 悪: test-author が読める範囲が広がる。テストの足場が本番のコードを import している場合、足場を通して実装の内部を知る経路ができる。足場が境界の型だけに頼っているかはレビューに残る。
- 悪: 技術部品の自己検査は作成者と判定者が同じになる。外から観測できる振る舞いに影響する部品は、REQ にしない限り独立に検証されない。
- 悪: 150 行という上限には根拠となる計測が無い。行数が少なくても写しは入りうる。

## 却下した選択肢

- **今のまま作業指針に宣言させ、レビューで量を抑える**: 規約が置き場所を決めていない限り、機能ごとに追記され続ける。検査の外にあるので止まらない。
- **作業指針の代わりに `TESTING.md` などの決まったファイル名を harness が指定する**: 置き場所は利用プロジェクトの構成によって違う。harness が決めるのは「作業指針に何を置かないか」と上限までにし、移し先はリンクで示させる。
- **技術部品にも REQ を書かせる**: R-401（外から観測できる振る舞いだけ）に反し、REQ が実装の設計を抱えることになる。
- **行数ではなく、写しを機械で検出する**: コードと文章の対応を機械で判定する方法が無い。行数は粗いが、確実に測れる。
- **上限を `traceconfig.json` で利用プロジェクトごとに変えられるようにする**: 上限を上げれば検査が意味を失う。作業指針を地図に限るのは方法論の決まりなので、値を固定する。
