# ADR-0050 develop-core を方法論に限り、組織とプロジェクトで変わる値は traceconfig.json の名前付きの差し込み口で受ける

## Context

develop-core には、性質の違う 2 種類の決まりが混ざっている。

- **方法論そのもの**: SSOT が先、作成者 ≠ 判定者、3 つの人間ゲート、成果物の型（UC・EARS の REQ・BR・`contract.yaml`）、完了条件（spec-lint・trace-check・contract-run）。trace-check の C1–C15 などの検査器はこの型が固定であることに依存しており、型を差し替えると完了を機械で判定できなくなる。
- **組織やプロジェクトの方針**: 会話と成果物の言語（日本語）、ブランチ名の形（動詞で始まる kebab-case の `<topic>`）など。組織が変われば変わる値だが、`develop/SKILL.md`・`attack/SKILL.md`・`comments.instructions.md`・`references/adr.md`・`references/commit.md`・`rules-cloudflare-hono-react` の 3 つの末端ファイルに直接書かれている。

後者が core にある限り、方針の違う組織が使うには core を書き換えるしかない。また core の外で方針を伝える口は「利用プロジェクトの `CLAUDE.md` / `AGENTS.md` に宣言があれば従う」という自由記述だけで、何でも入るため、利用プロジェクトの作業指針が膨らむ原因にもなっている（ある利用プロジェクトでは 1 つのユニットの `CLAUDE.md` が 1,135 行になった）。

一方、方法論そのもの（文書の型と作り方の流れ）を差し替え可能にすると、検査器とすべての agent の指示を抽象化することになり、core は何も保証しない殻になる。独自の文書の仕様や作り方の流れを持つ組織を「その組織の rules を書けば develop を使える」として受け入れることはできない。

## Decision

harness の資産を、変わり方ごとに 4 つの層に分ける。

| 層 | 持つもの | 変わる単位 | 置き場所 |
| --- | --- | --- | --- |
| 方法論 | 不変条件、成果物の型、担当の役割、3 つの人間ゲート、完了条件、検査器 | 変えない（変えるなら別の方法論として作る） | `develop-core`・`templates/`・`tools/` |
| 組織とプロジェクトの方針 | 言語など、値で表せる方針 | 組織・プロジェクト | 利用プロジェクトの `traceconfig.json` の `policy`（新設） |
| スタックの規約 | フレームワークの書き方、入口の命名、テストの足場 | 技術スタック | `rules-*` |
| プロジェクトの配置 | パス、コマンド、ユニット、ID の桁数 | プロジェクト | `traceconfig.json` の既存のブロック |

- **core は差し込み口を名前で持つ。** core が値を外から受けるときは、`traceconfig.json` のキー名で参照し、未宣言のときの既定値を明記する。「`CLAUDE.md` / `AGENTS.md` に宣言があれば従う」という自由記述の口を新たに足さない。
- **最初の差し込み口は `policy.language`**（会話と成果物の言語。BCP 47 の言語タグ。未宣言なら `ja`）。対象は会話・人間への報告、docs、契約の説明文、ADR、コミットメッセージ、コード内コメント、テストのタイトル、利用者向けの文言。既定を `ja` にするので、今の利用プロジェクトは何も変えずに同じ振る舞いになる。
- harness 自身のプロンプト正本の言語（ADR-0043）はこの判断の対象外で、日本語のまま。
- ブランチ名とコミットの形はすでに `git` ブロックと git-lint が受けている。`<topic>` の形を差し込み口にするのは、git-lint の変更を伴うので別の判断に残す。
- 3 つの人間ゲート、作成者 ≠ 判定者、成果物の型は方法論として core に残し、差し込み口にしない。
- 方法論を採らない組織は develop の対象外とする。harness の型へ移すときは `/docs-migrate` を使う。
- 強制: `policy.language` の値を読むのは各 agent で、機械の検査は無い（説得による統制。R-901）。

## Consequences

- 良: 言語など組織の方針を変えるのに core を書き換えなくてよい。core の変更は方法論の変更に限られる。
- 良: 方針を伝える場所が `traceconfig.json` のキーに決まり、利用プロジェクトの作業指針へ方針を書き足す理由が 1 つ減る。
- 良: 既定値が今の振る舞いと同じなので、利用プロジェクトの移行は要らない。
- 悪: `policy.language` が `ja` 以外のとき、harness のプロンプト正本（日本語）と成果物の言語が食い違う。agent が言語を取り違える危険は、実際のプロバイダーのセッションで確かめるまで残る。
- 悪: 差し込み口の値を検査する機械が無い。誤った値（存在しない言語タグなど）は agent が読むまで分からない。
- 悪: 独自の文書の型や作り方の流れを持つ組織は、develop を使うために harness の型へ移る必要がある。

## 却下した選択肢

- **組織やプロジェクトで変わるものをすべて `rules-*` に入れる**: `rules-*` は技術スタックの単位で選ぶパッケージで、組織の方針を混ぜると、スタックごとに同じ方針を写すことになる。値で表せる方針は文章の規約にせず、設定の値として持つほうが写しが生まれない。
- **文書の型と作り方の流れも差し替え可能にする**: 検査器（trace-check の C1–C15、spec-lint）が型の固定に依存しており、差し替えると完了を機械で判定するという develop の価値が消える。
- **方針は今のまま利用プロジェクトの `CLAUDE.md` / `AGENTS.md` に書いてもらう**: 自由記述の口は何でも受け入れるため、利用プロジェクトの作業指針が膨らみ続ける原因になる。
- **core を言語ごとに複製する**: 方法論の変更のたびに全言語版を直すことになり、知識を重複させない不変条件に反する。
