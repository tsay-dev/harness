# ADR-0067 REQ を 1 ID 1 ファイルで置くのをやめ、UC の文書の「要件」の節に小節として書く

## Context

要件（REQ）は、1 ID を 1 ファイル（`REQ-nnn.md`）で、属する UC のディレクトリに置いていた。利用プロジェクトの 1 つでは、UC 78 件に対して REQ のファイルが 1,197 件ある。

- 1 つの UC の仕様を読むのに、UC の文書と、平均 15 個の REQ のファイルを開く必要がある。人間が仕様を読み切るうえで、ファイルの数が妨げになっている。
- REQ のファイルは、どれも同じ形をしている（項目は 4〜5 個、見出しは 1 つ）。1,197 件すべてで、題は ID だけ、コメントはひな形の案内だけだった。ファイルを分ける理由になる中身の違いが無い。
- どの UC の要件かを、ファイルの置き場と、frontmatter の `uc` の 2 か所で表していた。食い違いを検査（R-1007）で見つけていたが、置き場だけで表せば、食い違いそのものが起きない。
- ひな形の案内のコメント（6 行）が、REQ のファイルごとに写されていた。

仕様を、断る条件の表や判定の表を使う書式へ書き直す案も試した（文書の量は約 3 分の 1 になる）。ただし、書き直した仕様が元と同じ意味かは機械で確かめられず、すべての UC で人間の確認が要る。今回は、意味を変えずに機械で移せる範囲にとどめる。

## Decision

- REQ は、属する UC の `UC.md` の `## 要件` の節に、1 ID を 1 つの小節（`### REQ-nnn`）として書く。`REQ-nnn.md` は置かない。
- 小節は、項目の並び（`- pattern:` / `- br:` / `- status:`。状態についての補足を書く任意の `- note:`）、要件文（`>` で始まる EARS の 1 文）、`#### 検証方針` の順に書く。
- REQ の小節は「要件」の節の中にだけ書く。節の外に書いた `### REQ-nnn` と、2 つ目の「要件」の節は違反にする（どの検査にも掛からない REQ を作らない）。
- どの UC の要件かは、書かれている `UC.md` で決まる。項目に `uc` は書かない。
- REQ の番号、状態（`draft` / `active` / `withdrawn`）、EARS の 1 文、検証方針と分割クラス、テストの注釈（`@covers REQ-nnn#class`）の意味は変えない。
- 読み方は `tools/_shared/reqs.mjs` の 1 か所に置く。spec-lint、trace-check、gate-hook は、小節から組み立てた REQ の文書（これまでの `REQ-nnn.md` と同じ形）に対して、これまでと同じ検査を行う。UC 自身の検査は、「要件」の節を除いた部分に対して行う。
- gate-hook は、`UC.md` への書き込みで、REQ の状態を下げる変更と、`active` な REQ の小節を消す変更に、人間の承認を求める（これまで `REQ-nnn.md` への書き込みで行っていた確認と同じ）。REQ の昇格と `active` での追加は、止めずに記録する。
- REQ の状態は、どのツールも同じ読み方で読む（小節から組み立てた文書の frontmatter として読む）。行末の案内のコメントの有無で、ツールごとに値が割れないようにする。
- `REQ-nnn.md` が残っていれば違反にする。移すスクリプト `harness migrate reqs`（`tools/docs-migrate/merge-reqs.mjs`）を用意する。スクリプトは、移した小節を読み戻して元と同じ中身になることを確かめ、合わないものが 1 つでもあれば何も書き換えない。落とすのは、ひな形の案内の文面と一致するものだけにする。`status` の値の後ろに案内に続けて書かれた文（撤回した理由など）は、項目 `note` に移す。
- ひな形は、`templates/develop/REQ.md` をやめ、`templates/develop/UC.md` の末尾に「要件」の節を足す。spec-lint は、UC と REQ の必須の項目を、どちらも UC のひな形から導く。
- 契約（`contract.yaml`）は、これまでどおり別のファイルに置く。契約の実例を実行する道具が読む形式で、文章の文書に混ぜると読み方が 2 つになるため。
- 強制の所在: `tools/docs-migrate/test/merge-reqs.test.mjs` が、節の読み方と、移す前後で中身が同じになること、移せないものがあれば書き換えないことを確かめる。spec-lint・trace-check・gate-hook のテストは、入力の REQ を「要件」の節に畳んだうえで、これまでと同じ検査が働くことを確かめる。

## Consequences

**得られるもの**

- 1 つの UC の仕様が、`UC.md` と `contract.yaml` の 2 つで読める。利用プロジェクトの 1 つでは、仕様のファイルが約 1,300 から 160 になる。
- 「REQ の `uc` が置き場と違う」「REQ の `id` がファイル名と違う」という食い違いが、形のうえで起きなくなる。
- ひな形の案内のコメントが、UC の文書に 1 回だけになる。

**代償と今後の制約**

- 利用プロジェクトは、版を上げるときに `harness migrate reqs --write` を実行する必要がある。自動では移らない。`REQ-nnn.md` が残っていると、spec-lint と trace-check が失敗する（移し方の案内は出る）。文書の中の `…/REQ-nnn.md` への参照は、手で `…/UC.md#REQ-nnn` に直す。
- `UC.md` が長くなる。REQ が 20 件を超える UC では、1,000 行を超える。1 つの REQ だけを読みたい・直したいときは、見出しで探すことになる。
- 複数の担当が同じ UC の別の REQ を同時に書き換えると、同じファイルへの書き込みになる。これまでは別のファイルだった。REQ の検証方針（テスト設計者が書く）と要件文（要件の作成者が書く）が、同じファイルに入る。
- git の履歴は、REQ ごとには追えなくなる（`UC.md` の履歴の中で追う）。
- 文章の重複や食い違い（REQ の要件文と、契約の誤りの一覧や UC の表が、同じことを別の言い方で書いているなど）は、この変更では減らない。減らすには、仕様を表の書式に書き直す必要があり、その確認は人間が行う。新しく書く UC・直す UC から順に進める。
- gate-hook の、REQ の状態の変化の確認は、`UC.md` の書き込みの前後で小節を読み比べる形になった。`UC.md` を Write で丸ごと書き直す書き込みで、ほかの REQ の小節を誤って消すと、承認の確認は出るが、どの小節が消えたかは最初の 1 件しか表示されない。

## 却下した選択肢

- **仕様を、断る条件の表と判定の表の書式に書き直す**: 文書の量は大きく減るが、書き直した仕様が元と同じ意味かを機械で確かめられない。すべての UC で人間の確認が要り、テストの紐づけも付け直しになる。一度に行うには大きすぎる。
- **REQ のファイルを残し、UC の文書から読み込む形の表示を作る**: 読むときのファイルの数は減るが、正本のファイルの数は変わらない。表示と正本の 2 つを持つことになる。
- **契約（`contract.yaml`）も `UC.md` に入れる**: 厳格な YAML の読み方と、文章の文書の読み方を 1 つのファイルで持つことになる。契約の実例を実行する道具と、契約を書く担当の入力が複雑になる。
- **検査ツールを、小節を直接読む形に書き直す**: 検査の中身（EARS の 1 文、検証方針、状態の決まり）は変わらないのに、3 つのツールの検査を書き直すことになる。小節から、これまでと同じ形の文書を組み立てて渡せば、検査はそのまま使える。
