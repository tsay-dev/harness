# ADR-0035 シナリオテスト（system suite）を UC 主シナリオの実行可能な写しとして phase の内側に置き、1 UC 1 本・境界でだけ走らせる

## Context

これまで system suite（ブラウザ・シミュレータ・実機を起動するテスト、`e2e/` / `UITests/`）は「場所だけ定めて develop の phase の外（opt-in）」だった。機械のオラクルは BE テスト（分割クラス、`@covers`）と契約例の実行（contract-run）が担い、FE は typecheck / lint と人間の目視・reviewer が担っていた。その結果、「部品は全部正しいのに繋ぐと動かない」種類の欠陥を機械が検知する手段が無く、また E2E をいつ・何本書くかが host の裁量に落ちて、書かれないか、実装の DOM に追随して書き直しが積もるかのどちらかになっていた。

E2E は DOM / 画面構造に依存するので開発中は壊れやすい、という懸念は半分正しい。ロケータが実装詳細（CSS 構造）を固定すると壊れるが、ユーザーに見える情報（role / 文言）と観測可能な結果だけを断言するなら、それは「ユースケースの振る舞い」を固定しているのであり、振る舞いが変わったときにだけ壊れる。そのとき書き直すのは正当なコストである。

一方で E2E は遅く flaky なので、赤緑ループに混ぜると Phase 4 が回らなくなる。本数の上限と、走らせる瞬間の限定が要る。

## Decision

- **SSOT は `UC.md` の主シナリオと事後条件**である。シナリオテストはその実行可能な写しであり、主シナリオに無い手順を足さない。UC を書き換えずにテストへ手順を足すことは禁止（R-801 の適用。`docs.instructions.md` R-1106〜R-1108）。
- **1 UC につきシナリオテスト 1 本、正常系のみ。** 失敗系・境界は従来どおり REQ の分割クラス → デフォルトスイート。本数の上限が UC 数で決まるため、system suite が無制限に増えない。
- **書く時期は契約 `fixed` 直後、Phase 4 の並列起動と同時。** `test-author (track: scenario)` が UC ディレクトリと契約だけから書く（実装は読まない。ADR-0036）。実装が配線されるまでは pending マーカー付きの Red として filing し、FE 配線の `implementer (logic)` がマーカーを外して Green にする。
- **走らせる瞬間は境界だけ。** 修正ラウンドでは当該 UC の 1 本を選択実行するのみ、終端リストと CI では全件を 1 回。デフォルトスイートと同じく、修正ラウンドで system 全件を撃つことは禁止。
- **機械検査**: `trace-check` に C15 を追加する — `tests.system` を宣言した host では、アクター種別が人間の `active` UC はすべて `@scenario UC-nnn` を持つシナリオテストを 1 本以上持つ。`stop-gate` は `commands.system` が宣言されていれば終端リストの最後（test の後）に走らせ、無ければ `skip` として報告する。完成の定義（`develop/SKILL.md` §2）にこの 2 項を加える。
- **プローブは変えない。** walking skeleton は引き続き browser E2E を要求しない使い捨て。会話で言う「最初のスモーク 1 本」は、最初に `完了` する UC のシナリオテストがその役を担う。

強制の所在: 本数と存在は C15、境界での実行は `stop-gate`（宣言時）と CI、赤緑ループへの混入禁止は各 rules-* の testing 葉（discovery からの除外）と `playbook.md` *Test-run granularity*。

## Consequences

- 「繋ぐと動かない」を機械が終端で拾えるようになり、FE の欠陥を目視と reviewer だけに頼らなくなる。
- 終端リストが 1 項目伸び、`commands.system` を宣言した host では変更のある Stop ごとに system 全件が走る。シミュレータ起動が重い host は宣言せず CI だけに置く選択肢を残す（宣言しないことは `skip` として見える）。
- UC の主シナリオを「アクターの観測可能な操作 / システムの観測可能な応答」で書く規律が求められる。画面構造を書けば写しが実装に寄る。
- 目視ゲートでレイアウト・装飾を変えてもテストは壊れない（role・文言・事後条件しか断言しないため）。DOM 構造を断言したテストは reviewer の「シナリオ」角度で `持ち越し` になる。
- シナリオテストが境界で赤になったとき、原因は 3 通りある（実装の欠陥 / テストが実装詳細を固定 / UC 自体が違う）。orchestrator は必ずこの順で診断し、「テストが落ちたから UC を直す」へ直行しない（`playbook.md` *Routing information*）。
- Web とモバイルの両 surface を持つ UC は C15 では「1 本以上」で通る。surface ごとに必須にする拡張は今回入れない。

## 却下した選択肢

- **開発がひと段落してから最後にまとめて書く**: 「最後」は来ない（次の機能に着手している）。機能が増えた中盤にリグレッション検知が無く、E2E の価値を一番受けたい時期に受けられない。
- **Playwright / XCUITest のテストコードそのものを SSOT にする**: テストコードは「何が起きるべきか」しか持てず「なぜ」を持てない。SSOT を UC に置き、テストを写しにすることで、変更時に「このテストを変えてよいか」を UC で判定できる。
- **失敗系もシナリオテストに書く**: 本数が分割クラス数に比例して増え、system suite が遅く flaky になる。失敗系は契約の `errors` と分割クラスで機械が既に判定している。
- **system suite を赤緑ループ（`commands.test`）に入れる**: ブラウザ / シミュレータが排他資源で並列セクションと衝突し、Phase 4 が回らない。
- **C15 を UC frontmatter の新キー（`scenario:`）で判定する**: SSOT が増え、spec-lint の閉じた語彙も増える。アクター種別（`02-actors.md`）は既にあり、UC の `actor:` から機械で辿れる。
