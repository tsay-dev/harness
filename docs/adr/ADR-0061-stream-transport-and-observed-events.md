# ADR-0061 持続する接続のメッセージを stream として契約に書き、届くイベントを観測者ごとに例で照合する

## Context

境界契約（ADR-0001）は一つの書式で HTTP と非 HTTP の境界を扱い、contract-run（ADR-0032）が例を実装に対して実行する。しかし `transport` の語彙に持続する接続（WebSocket、SSE）が無く、例は「要求 1 件に応答 1 件」しか表せなかった。

リアルタイムに状態を同期する利用プロジェクトでは、境界の主要部分が次の形を取る。

- ある利用者の操作の結果が、応答ではなく、別の接続へのイベントとして届く。
- 届く相手が一様でない（同じ部屋にいる相手にだけ届く、本人には届かない）。
- 操作によらず届くイベントがある（時間経過による退席、認証の失効）。

これらを契約に書けないと、境界の形が機械検査の外に置かれ、実装・テスト・クライアントが契約以外の場所で形を合わせることになる。`push` は「届くペイロード」を書けるが、きっかけと宛先を書けず、例を実行できない。

## Decision

1. `transport` に `stream` を追加する。持続する接続の上を流れるメッセージを表し、WebSocket と SSE を区別しない。`entry` にメッセージ種別を書く。`direction: outbound` は送るメッセージ（`request` / `response` / `errors` は従来どおり）、`direction: inbound` は届くイベント（形は `push` と同じく `request` に書き、`response` と `errors` は持たない）。接続の確立と認証は従来の `http` の操作として書く。
2. 契約の最上位に `observers:`（名前: 1 行の説明）を追加する。イベントが届く相手を、利用プロジェクトの言葉で宣言する。harness が予約する名前は `self`（例の主体の接続）だけとする。
3. `stream` の例に `events:` を追加する。観測者ごとに、届くイベントを `{ entry, payload }` の列で順に書く。書いた観測者の `[]` は「届かない」の宣言で、書いていない観測者は照合しない。`fixed` の `stream` の例は `events:` を省略できない。
4. 操作によらず届くイベントは、そのイベント自身の例（`events:` だけを持つ例）に書く。状況は従来の `case` 名による事前状態と同じく、利用プロジェクトのアダプターが作る。届くイベント自身の例は任意だが、`fixed` ではどの例の `events:` にも現れない届くイベントをエラーにする。
5. contract-run はアダプターへの要求に `observe`（照合する観測者名）を渡し、応答の `events` を観測者ごとに照合する。種別・件数・順序は完全一致、`payload` は従来の応答と同じ部分集合の一致とする。失敗例でも照合する。

保証箇所: 語彙と書式（`stream`、`entry` 必須、観測者名の解決、`events` 項目の閉じたキー、`entry` と `payload` の届くイベントへの解決、`fixed` での省略禁止と未出現の検出）は spec-lint。実装との一致は contract-run。操作のキーは 13 個のまま変えない（`events` は例の中、`observers` は最上位に置く）。

## Consequences

- リアルタイム同期の境界を、HTTP と同じ契約ファイル・同じ検査で扱える。「届くべきでない相手に届いた」「余分なイベントが出た」を例で検出できる。
- 既存の SSE 配信も同じ語彙で契約に載せられる。
- アダプターの責務が増える。観測者ごとの接続を用意し、例ごとに届いたイベントを集めて返す必要がある。観測者の事前状態（どの部屋にいるか）は観測者名と `case` 名からアダプターが決めるため、その対応の正しさは利用プロジェクトの責任で、機械は検査しない（R-901）。
- 順序を完全一致にしたので、配信順が保証されない実装は例を通せない。順序に意味が無い配信でも、実装は決定的な順序を持つ必要がある。
- 「イベントが届かないこと」は、アダプターが収集を打ち切る時点までしか観測できない。プロセス内で同期的に配信を集められない実装では、待ち時間の設計がアダプターに必要になる。
- 接続の寿命（切断、再接続、バックプレッシャー）と、メッセージ列にまたがる状態遷移は契約の対象外のままで、UC / REQ とテストが扱う。

## 却下した選択肢

- **AsyncAPI を別ファイルで持つ**: 標準書式だが、一つの書式で全境界を扱う判断（ADR-0001）と衝突し、spec-lint・contract-run・`@operation` の紐づきを二系統に分けることになる。
- **届くイベントの形だけを定義し、きっかけと宛先は書かない**: 変更は最小だが、契約検証が見るのがペイロードの形だけになり、誤配信と過剰配信がテスト任せになる。
- **宛先を `self` / `others` の固定 2 種にする**: 一部の接続にだけ届く配信を例で表せない。宛先の区別はリアルタイム境界の形そのものなので、利用プロジェクトの言葉で宣言できるようにした。
- **届いたイベントを含有（部分集合）で照合する**: 例は壊れにくいが、余分なイベントと届くはずのない相手への配信を検出できない。
- **件数と種別だけ一致させ順序を問わない**: 順序が意味を持つ配信（参加の通知の後に参加者の一覧、など）を検査できない。
- **`websocket` と `sse` を別の transport にする**: 方式ごとの制約を lint で強制できるが、契約が表すのはメッセージの形と向きであり、方式の違いは `direction` で足りる。語彙を増やす理由にならない。
- **既存の `push` を拡張する**: `push` は OS の通知ペイロードを指す語として使われており、双方向のメッセージと観測者を載せると既存の契約の意味が変わる。
