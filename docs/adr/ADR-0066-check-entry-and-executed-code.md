# ADR-0066 テストが本番と同じ組み立てを通ることと、実行されなかったソースが無いことを、実行の記録で確かめる

## Context

仕様と実装の紐づきは、コードに書く注釈（`@implements` など）と、テストに書く注釈（`@covers` など）で確かめている。注釈は名乗りであり、書けば通る。テストが通っていても、次のことは確かめられていない。

- テストが、本番と同じ組み立てを通っているか。利用プロジェクトの 1 つで、テストの入口が機能の経路と依存を自分で組み直していた。本番の組み立てにだけある、エラーの扱い・1 つの経路・未知の API への応答が、既定のテストから外れていた。本番の依存の組み立てのファイルは、実行された行が 51% だった。
- どのテストからも実行されないコードが残っていないか。同じプロジェクトで、1 行も実行されないソースのファイルが 6 つあった。

どちらも、注釈の検査では見つからない。テストの入口を本番の組み立てに通し直したところ、テストは 1 件も直さずに通り、本番の依存の組み立ての実行された行は 86% になった。直す手間は小さく、見つける手段が無かったことが問題だった。

## Decision

- 設定に、本番の組み立てとテストの入口を書く欄 `entry`（`compose` と `test_entry`。どちらも `<ファイル>#<名前>`）を足す。
- 設定に、テストが書き出す実行の記録を書く欄 `coverage`（`report`、`scope`、`not_run`）を足す。記録の形式は lcov にする。
- `tools/exec-check` を足す。入口からは `harness lint entry` と `harness lint coverage`。ファイルと記録を読むだけで、テストは実行しない。
  - `lint entry`: テストの入口のファイルの中に、本番の組み立ての名前が現れること。
  - `lint coverage`: 範囲に入るソースのファイルが、すべて記録に載り、実行する行を持つファイルは 1 行以上実行されていること。本番の組み立てのファイルが実行され、記録に関数ごとの情報があれば、組み立ての関数が 1 回以上呼ばれていること。
- どのテストからも実行されないことを認めるファイルは、`coverage.not_run` に理由と一緒に書く。書いたファイルが実行されるようになったら違反にする（古い宣言を残さない）。
- 記録で確かめる範囲は `coverage.scope` で絞れる。範囲の外のソースは確かめず、件数を毎回表示する。
- 確かめるのは「1 行も実行されなかったファイルが無いこと」までにする。行ごとの割合のしきい値は持たない。
- 完了の判定（`tools/gate-hook/suite.mjs`）に加える。`lint entry` は読むだけの検査として level `lint` 以上で、`lint coverage` は `commands.test` が通った直後に level `fast` 以上で実行する。記録が `commands.test` を始めた時刻より新しいことを確かめる。
- `entry` と `coverage` は、`{ "none": "<理由>" }` と書ける。省略したものは「未宣言」と表示する。どちらも違反にはせず、確かめていないことを毎回表示する。
- 強制の所在: `tools/exec-check/test/exec-check.test.mjs` が、検査項目 X1・X2・V1〜V5 のそれぞれについて、状態を 1 つ変えると落ちることを確かめる。`tools/gate-hook/test/stop-gate.test.mjs` が、完了の判定の中での順序と、`--since` を渡すことを確かめる。

## Consequences

**得られるもの**

- テストの入口が本番とは別の組み立てを通っていることと、どのテストからも実行されないコードが、機械で見つかる。
- 実行されないことを認めたファイルが、理由と一緒に一覧で見える。
- 注釈による紐づき（`@implements`）を外す前提がそろう。コードが仕様のテストから実行されていることを、注釈ではなく記録で言えるようになる。外すかどうかは、別に決める。

**代償と今後の制約**

- 利用プロジェクトは、テストのコマンドが lcov の記録を書き出すように設定する必要がある。記録を取る分、テストの時間が増える（利用プロジェクトの 1 つでは約 6%）。範囲に入るソースを、実行されなかったファイルも含めて記録に載せる設定も要る。
- `lint entry` が確かめるのは、名前がファイルの中に現れることだけである。呼んでいるか、コメントに書いてあるだけかは区別しない。別のファイルを経由して呼ぶ形は、名前が現れないので違反になる。実際に呼ばれたことは、`lint coverage` で確かめる。記録に関数ごとの情報があれば、組み立ての関数が呼ばれた回数を見る。無ければ、確かめられるのは組み立てのファイルが読み込まれたことまでである。`coverage` を宣言していなければ、この裏付けは無い。
- 1 行でも実行されたファイルは通る。ファイルの中の一部の関数が実行されないことや、実行された行が正しい結果を確かめるテストから実行されたかは、確かめない。
- 仕様のテストが、テストの入口を通らずに本番のコードを直接読み込むことは、この検査では止まらない。利用プロジェクトの lint の規則で止める。
- `entry` と `coverage` を省略しても、none と書いても、失敗にならない。確かめていないことは表示されるが、表示を読まなければ気付かない。紐づきの宣言（省略は設定エラー。ADR-0056）より緩い。利用プロジェクトが記録の書き出しを整えるまでの間、版を上げただけで失敗しないようにするためである。必須にするかどうかは、利用プロジェクトの移行が済んでから決める。
- 画面のコードのように、既定のテストでは実行されないソースは、`coverage.scope` で外す。外した範囲は、この検査では何も確かめていない。
- 記録は 1 つのファイルだけを読む。テストの種類ごとに別の記録を書き出すプロジェクトは、1 つにまとめてから渡す。
- harness 自身は、`entry` と `coverage` を none にしている。同梱ツールのテストがツールを別のプロセスとして起動するので、実行の記録を 1 つにまとめる仕組みが要る。

## 却下した選択肢

- **行ごとの割合のしきい値を持つ**: 数字を満たすために、意味の薄いテストを足すことになる。割合が高くても、テストが別の組み立てを通っていれば裏付けにならない。先に確かめるべきは、組み立てと、まったく実行されないファイルである。
- **テストの入口と本番の組み立ての一致を、コードの構文を読んで確かめる**: 言語とフレームワークごとに読み方が違い、harness が言語ごとの解析を持つことになる。名前が現れることを文字で見て、実際に通ったことは実行の記録で確かめる。
- **harness がテストを実行して記録を取る**: テストの実行のしかたは、利用プロジェクトのコマンドが決める。harness は、決められた形式の記録を読むだけにする。
- **記録の形式を、道具ごとの独自の形式（JSON の要約など）にする**: 道具を変えると読めなくなる。lcov は、多くの言語の道具が書き出せる。
- **`entry` と `coverage` を最初から必須にする**: 版を上げたとたんに、記録の書き出しを整えていない利用プロジェクトの完了の判定がすべて失敗する。
