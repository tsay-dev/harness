# ADR-0070 手で書く紐づきをテストの側に集め、実装との対応は実行の記録と入口の一覧で確かめる

## Context

仕様とコードの紐づきは、4 種類の注釈で確かめてきた。テストの `@covers` とシナリオテストの `@scenario`、実装とスキーマの `@implements`、入口と外部境界のクライアントの `@operation` である。実装の側の 2 つには、次の問題があった。

- **書けば通る。** `@implements REQ-nnn` は、その単位が要件を実現していることを示さない。機械が見るのは、注釈があることと、指す ID が実在することまでである（ADR-0019、ADR-0055 が、意味の確認を reviewer に残している）。同じことを、テストは実行して確かめている。注釈は、テストが既に持っている裏付けを、手で書き写したものになっていた。
- **書く量と、検査の仕組みが大きい。** 実現単位ごとの `@implements`、入口ごとの `@operation`、制約ごとの `@implements` を書かせるために、単位・入口・制約を行の正規表現で探す設定（`unit_pattern`、`entry_pattern`、`constraint_pattern` など）と、ソースの全ファイルを実現単位の置き場か技術部品の置き場に分類する宣言（ADR-0055）を、利用プロジェクトごとに保つ必要があった。行の正規表現は、パスがリテラルで始まらない入口などを取りこぼし、取りこぼした入口は検査から見えなかった。
- **契約に無い入口を、注釈では見つけきれない。** 注釈を探す検査から見えるのは、正規表現が拾えた入口だけである。

一方で、実装との対応を実行で確かめる手段は、ADR-0066 でそろい始めていた。テストが本番と同じ組み立てを通ることと、どのテストからも実行されないソースのファイルを、実行の記録で見つけられる。ADR-0066 は「注釈による紐づき（`@implements`）を外す前提がそろう。外すかどうかは、別に決める」としていた。この ADR が、それを決める。

依頼主と合意した方針は次のとおり。

- 仕様と実装が紐づいていることは、機械で確かめられる状態を保つ（目的は品質）。
- 手で書く紐づきは、テストの側だけにする。実装のコードに印を書かない。
- 実装との対応は、印ではなく、実行して確かめる。
- 契約に無い入口は、機械で見つける。

## Decision

### 1. 手で書く紐づきは、テストの注釈の 2 種類だけにする

- テストの `@covers`（REQ のクラス `@covers REQ-nnn#class`、NFR `@covers NFR-nnn`、規則 `@covers BR-nnn`）と、シナリオテストの `@scenario UC-nnn`。
- `@covers BR-nnn` を足す。クラスは付けない。正規表現は設定の `br_pattern`（省略できる）。数えるのは `tests` の範囲だけで、シナリオテストに書かれたものは違反にする。

### 2. 実装とスキーマの `@implements` を読まない

trace-check の検査を、次のように外し、変える。番号は詰めない（過去の記録の番号と食い違わせない）。

| 検査 | 変更 |
| --- | --- |
| C5（存在しない・撤回済みの ID を `@implements`） | 廃止 |
| C14（active な REQ・BR に `@implements` が無い） | 廃止 |
| C19（実現単位が `@implements` を持たない） | 廃止 |
| C23（スキーマの制約が `@implements` を持たない） | 廃止 |
| C27（ソースのファイルが実現単位の置き場にも技術部品の置き場にも入らない） | 廃止 |
| C1 | 「active な REQ に、保留でないテストの `@covers` が無い」だけにする。実装が残る draft の REQ にテストを求める部分をやめる |
| C13 | 置き換える。`enforced_at` が DB を指す active な BR に、保留でないテストの `@covers BR-nnn` が無ければ違反 |
| C22 | 緩める。active な BR は、`br:` に持つ active な REQ があるか、保留でないテストが `@covers BR-nnn` していれば通る |
| C3 / C11 | `@covers BR-nnn` を扱う。未定義・撤回済みの BR を指せば C3。`@covers BR-nnn` だけを持つテストは、注釈のあるテストとして数える |

DB で守る規則は、制約が効くことをテストで確かめる。テストは、アプリの入口を通さずに、規則に反する行を DB に直接入れて、断られることを確かめる。実 DB が要るので、置き場は、スタックの規約が実 DB のテストに定めるスイート（結合スイートなど）にする。置き場は `tests.dirs` の中で、`commands.test` か `commands.extra` のどれかが実行するものでなければならない。test-author は、このテストを書くときに限り、スキーマ正本（表・列・制約の定義）を読んでよい（実装を読まない決まりの例外。スキーマは人間が承認した DB 設計の正本で、ロジックではない）。そのため、スキーマの承認の後に起動する。`enforced_at` が DB を指すかどうかは、`database`・`db`（語として）と「データベース」「ＤＢ」で判定する。入口を通すと、手前の検証が断ったのか DB の制約が断ったのかを区別できないためである。

### 3. 入口の `@operation` を読まず、アプリが出す入口の一覧を契約と突き合わせる

- C21 を廃止する。
- 利用プロジェクトは、設定の `commands.list_entries` に、アプリの入口の一覧を標準出力へ 1 行 1 件の JSON で出すコマンドを書く。コマンドか、理由付きの none を必ず書く。none が通るのは、撤回されていない UC の fixed の契約に inbound の操作が 1 つも無い間だけ（0 行の一覧が通る条件と同じ）。
- 1 行の形は、http なら `{"kind":"http","method":"GET","path":"/api/members/:accountId"}`、それ以外は `{"kind":"deeplink","name":"<契約の entry>"}`（`kind` は契約の transport と同じ語。契約に `entry` を持たない transport は、操作の名前）。
- exec-check に `entries` を足す（入口からは `harness lint entries`）。
  - E1: 一覧にある入口が、撤回されていない UC の fixed の契約の、inbound の操作のどれにも合わない。fixed でない契約の操作は、突き合わせ先に数えない。契約の fixed への昇格には人間の承認が要り（ADR-0057）、fixed の契約の操作には実例が必須になるが、draft の契約は承認なしに書ける。draft の契約の操作を数えると、操作を 1 つ書き足すだけで、REQ もテストも実例も無い入口が通る。合う操作が fixed でない契約にしか無い入口は、合う操作と契約の `x-status` を示して違反にする（同じ E1。文を分ける）。
  - E2: fixed の契約の、owned かつ inbound の操作に合う入口が、一覧に無い。
  - E3: 欠番（下の「契約の外の入口を認める手段を作らない」）。
  - E4: 一覧か、契約の `wire.path` を読めない（契約の inbound の操作の `wire.path` が書式に無い形を含む、未宣言、none にできないのに none、fixed の契約に inbound の操作があるのに 0 行、JSON でない行、項目の欠落、同じ入口の重複、決まった書式に無い形を含むパス、廃止した設定のキー `entries`）。
- **契約の外の入口を認める手段を作らない。** アプリの入口は、すべて契約の操作として書く。当初の案には、契約に書かない入口を理由と一緒に設定に書く宣言（`entries.outside_contract`）と、その古い宣言を見つける検査（E3）があった。この宣言で認めた入口は、契約に無く、テストも求められない。入口の処理は無名の関数で書かれることが多く、関数の単位の検査（V6）にも掛からない。設定に 1 行足せば、仕様にもテストにも無い入口を置けることになるので、この宣言そのものを廃止した。生存確認、準備の確認、静的なファイルや画面の配信のような、機能の仕様ではない入口も契約に書く。運用のための入口をまとめる UC を 1 つ立て（アクターの種別は「システム」。人間でないアクターの UC にシナリオテストの義務は無い）、何でも受ける経路は `wire.path` に `/assets/*` のように書き、応答が JSON でない操作は、アダプターが返す JSON の形（`contentType` など）を `response` と実例に書く。契約の書式（spec-lint）と contract-run は、変えずにこの形を扱える。設定に `entries` が残っていれば、廃止したキーとして失敗にする。
- http の入口は、method と完全なパスで突き合わせる。一覧のパスの書式は harness が決め、特定の枠組みの書き方には合わせない。パラメーター 1 つは、区分の全体が `:name` か `{name}` の形（2 つは同じに扱う。名前は、英字か `_` で始まる英数字・`_`・`-`）、何でも受ける部分は `*`（`**` も同じ）だけを読む。それ以外の形（`[...slug]`、`{*splat}`、`:rest{.+}`、`{path:path}`、`:id?` など）を含む行は、読めない行として違反にする（E4）。こういう形は、受ける区分の数や省略できるかどうかが枠組みごとに違い、パラメーター 1 つとみなすと、契約より広い入口が契約の `/x/{id}` に合ったことになる。枠組みの書き方をこの書式に直すのは、一覧を出すスクリプトである。何でも受ける登録の `*` は、パラメーター 1 つとは別のものとして扱い、契約の `wire.path` も `*` と書いてあるときだけ合う（`/x/*` の入口を、契約の `/x/{id}` に合ったことにしない）。これまでの C21 は、入口の接頭辞が分からないので後方一致で比べ、method を見なかった。一覧はアプリ自身が出すので、完全なパスと method で比べられる。
- exec-check は、ファイルと記録を読むだけで、コマンドを実行しない（ADR-0066）。コマンドは検査の並び（`tools/gate-hook/suite.mjs`）が level `fast` 以上で実行し、標準出力を一時ファイルに書いて渡す。位置は、テストの入口の検査（`entry`）の次、契約の実例の実行（contract-run）の前。level `lint` では skip として表示する。none と未宣言の判定は、契約を読めば分かるので、level `lint` でも行う。`a | b` の形のコマンドは、シェルが対応していれば pipefail を付けて実行する。monorepo では unit の設定に書く（ルートの設定に書いたコマンドは実行されないので、config-lint の K7 が違反にする）。
- 一覧を出すスクリプトは、implementer（`logic`）が、入口を足す・変える・消すのと同じ変更で書いて保つ。最初の 1 本の形は、スタックの規約（`rules-*` の `harness.config.json` の規約）が示す。

### 4. 実行の記録の検査を、関数の単位まで細かくする

実装の印を外した後、撤回した要件のコードが残っていることは、3 段で見つける。

1. 撤回した要件を `@covers` するテストは、違反になる（今ある C3）。テストを消すことになる。
2. 契約から消した操作の入口は、契約に無い入口として違反になる（E1）。入口を消すことになる。
3. テストも入口も無くなった先の処理は、どのテストからも実行されないコードとして違反になる（exec-check の coverage）。

3 がファイルの単位のままだと、ほかの関数が使われているファイルの中の、どこからも呼ばれない関数を見逃す。そこで、coverage に次を足す。

- V6: 範囲に入るソースの、名前のある関数のうち、記録（lcov の `FN` / `FNDA`）で 1 回も呼ばれなかったものを違反にする。
- V7: 記録に関数ごとの情報が 1 つも無ければ違反にする。出さない道具を使うなら、`coverage.functions` を `{ "none": "<理由>" }` と書く。その間は、ファイルの単位までしか確かめていないことを毎回表示する。none にできるのは、記録に関数ごとの情報が 1 つも無いときだけ（あるのに none なら違反）。ほかのファイルには `FN` / `FNDA` があるのに、行の情報を持つファイルに、`FN` / `FNDA` も、関数を持たないことを示す `FNF:0` も無ければ、そのファイルを違反にする。`FNF:0` は関数を持たないファイルの見分けにだけ使い、「記録に関数ごとの情報がある」ことの根拠には数えない（すべてのファイルが `FNF:0` だけの記録は、関数ごとの情報が無い記録として違反にする）。
- 呼ばれないことを認める関数は、`coverage.not_run` に `<ファイル>#<関数の名前>` で、理由と一緒に書く（`entry` の `<ファイル>#<名前>` と同じ書き方）。認めた関数が呼ばれるようになったら違反にする（V4。ファイルの単位の決まりと同じ）。
- 名前の無い関数（記録の名前が `(` か `<` で始まるものと、`anonymous_<数字>` の形のもの。無名のコールバックなど）は、対象にしない。道具が付ける仮の名前（Istanbul の `(anonymous_3)`、Node の `anonymous_3` など）は編集のたびに変わるので、認める項目として指せない。
- 同じ名前の関数が 1 つのファイルに複数あるときは、呼ばれた回数を足して数える（記録は名前でしか区別できない）。
- 割合のしきい値は持たない（ADR-0066 のまま）。
- **active な REQ があり、`source` を宣言しているプロジェクトは、`coverage` を none にも省略にもできない**（trace-check の義務表、C26）。実装の印を外した後、実装と仕様の対応を確かめる検査は、実行の記録のほかに無い。none を認めると、その検査が 0 になる。記録のファイル（`report`）を指していない宣言（`{}`、`null`、文字列）も、同じく C26 が違反にする。ADR-0066 は「`entry` と `coverage` は省略しても失敗にしない」としていたが、`coverage` については、要件とソースがある場合に限って、この ADR が置き換える。`entry`（テストの入口が本番の組み立てを通ること）は、組み立てとテストの入口が分かれないスタックがあるので、義務にしない。

### 5. 廃止したキーを、黙って読み飛ばさない

- 廃止する設定のキー: `implements_pattern`、`operation_pattern`、`source` の `unit_dirs`・`support_dirs`・`unit_pattern`・`implements_placement`・`entry_pattern`・`entry_exclude`・`entry_file_pattern`、`schema` の `constraint_pattern`・`implements_placement`。どれも、廃止した検査だけが読んでいた。`source.dirs`・`extensions` と `schema.files`・`dirs` は残す（層の向き C6、用語集の識別子 C25、実行の記録の範囲が読む）。契約の外の入口を認める宣言 `entries` も、同じ一覧に入れる。
- 設定に残っていたら、config-lint（K6）と trace-check が、キーごとに代わりにすることを添えて失敗にする。一覧の正本は `tools/_shared/config.mjs`。古い設定ファイルの名前（ADR-0064）と同じ扱いである。
- `--only` に廃止した検査の番号を渡すと、使い方エラーにする。

### 6. 索引から、要件を確かめるテストを引けるようにする

`harness index` が、REQ・BR・NFR ごとに `tests:`、UC ごとに `scenario:` の行で、その ID を指すテストのファイルを出す。実装に印が無くなるので、要件から実装を辿る入口は、要件のテストになる。

### 強制の所在

- `tools/trace-check/test/links.test.mjs`: C13、C22、C3 / C11 の BR の扱い、`coverage` の義務（C26）、廃止したキーと検査の番号、索引のテストのファイル。
- `tools/exec-check/test/exec-check.test.mjs`: E1・E2・E4 と V6・V7・V4 のそれぞれについて、状態を 1 つ変えると落ちること。契約に無い入口は、設定に何を書いても必ず違反になること。
- `tools/gate-hook/test/stop-gate.test.mjs`: 検査の並びの中の位置、一覧のコマンドを unit のディレクトリで実行して標準出力だけを渡すこと、level `lint` での skip。
- `tools/config-lint/test/config-lint.test.mjs`: K6・K7。
- 手順・担当・規則の文（`packages/`）は、実装に印を書かないこと、DB で守る規則のテストの書き方を定める。文だけで強制している部分は、テストが入口を通さず DB に直接入れているかどうかと、`tests.dirs` のテストを `commands.test` か `commands.extra` が実行していること、入口の一覧を本番と同じ組み立てから列挙していることである（機械が見るのは `@covers BR-nnn` があることまで。reviewer が見る）。

### 過去の ADR との関係

過去の ADR の本文は書き換えない。全体を置き換えるのは ADR-0019 だけなので、この ADR の `supersedes` に書き、ADR-0019 の status を superseded にした（`references/adr.md` の決まり）。ほかの ADR は一部だけを置き換えるので、status は変えず、置き換える部分をここに書く。

- **ADR-0019**（active な REQ / BR に `@implements` を必須にする。C14）: 全体を置き換える（superseded）。C14 を廃止した。
- **ADR-0055**（ソースの全ファイルを実現単位の置き場か技術部品の置き場に分類する）: 分類（`unit_dirs` / `support_dirs`、C19、C27）を置き換える。コードに書く仕様外の印を持たないことと、仕様を持たないテストを `tests.dirs` の外に置くこと（C11）は、そのまま効く。
- **ADR-0056**（紐づきに例外を作らない）: そのまま効く。baseline、警告だけの違反、コードに書く例外の印は持たない。例外（`coverage.not_run`）は、設定に理由と一緒に書かせ、当てはまらなくなったら違反にする。契約の外の入口には、例外を認める手段そのものを作らない。義務表から、廃止したキーの行を除いた。C21 のパスの照合の限界（短い捕捉が別の操作に一致しうる、method を見ない）は、入口の一覧の突き合わせに替わって無くなった。
- **ADR-0066**（テストの入口と実行の記録）: 土台にして広げる。coverage を関数の単位まで細かくし、exec-check に entries を足した。「読むだけで実行しない」「割合のしきい値を持たない」は、そのまま保つ。「`entry` と `coverage` を省略しても失敗にしない」は、`coverage` について、active な REQ と `source` がある場合に限って置き換える（上の 4）。`entry` は変えていない。
- **ADR-0004**（DB 設計の正本はネイティブのスキーマ）: そのまま効く。スキーマの制約に注釈を書く決まりだけを、テストで確かめる決まりに替えた。

## Consequences

**得られるもの**

- 実装のコードに、検査のための印を書かなくてよい。書く量が減り、要件を撤回したときに直す場所がテストと契約だけになる。
- 利用プロジェクトが保つ設定が減る（単位・入口・制約を探す正規表現、置き場の分類）。行の正規表現の取りこぼしで、入口が検査から黙って外れることが無くなる。
- 契約に無い入口が、機械で見つかる。method の違いも見つかる。
- DB で守る規則が、注釈ではなく、制約が実際に断ることで確かめられる。
- 撤回した要件のコードは、テスト（C3）、入口（E1）、どこからも呼ばれない関数（V6）の 3 段で、消すところまで機械が求める。

**代償と今後の制約**

- **撤回した要件のコードが、ほかのテストから実行されている限り、残っても見つからない。** まだ呼ばれている関数の中の枝として残る処理（撤回した要件のための分岐など）は、関数が 1 回でも呼ばれていれば通る。撤回のときに「その要件のテストだけが実行していた行」を出す道具で補う余地があるが、今回は作らない。
- **コードを読んだその場で、どの要件のためのコードかが分からない。** 辿るには、`harness index` で要件のテストを引き、そのテストが実行するコードを見る。逆向き（このコードはどの要件か）を直接引く手段は無い。
- **どの規則にも対応しない DB の制約は、検出しない。** スキーマの制約を読まなくなった（これまでは C23 が、注釈の無い制約を違反にしていた）。reviewer が見る。
- **`@covers BR-nnn` のテストが、本当に DB に直接入れているかは、機械では確かめない。** 入口を通すテストに `@covers BR-nnn` を付けても C13 は通る。
- **テストが実際に実行されたかは、プロジェクトの `commands` の宣言に依る。** C13 を含め、trace-check が見るのは注釈があることまでである。`tests.dirs` のテストを `commands.test` か `commands.extra` のどれかが実行する、という決まりは文書で求めているが、機械では確かめていない。DB で守る規則のテストは、既定のテストから外した結合スイートに置くことが多く、そのスイートのコマンドを `commands.extra` に書き忘れると、実行されないまま C13 が通る。
- **fixed の契約の、outbound の操作と `owned: false` の操作に、実装との対応の検査が無くなった。** 以前の C21 は、fixed の契約のすべての操作が、どこかの `@operation` から指されることを求めていた。`owned: true` の outbound の操作は、契約の実例の実行（contract-run）がアダプターを通して実行する。`owned: false` の操作は、既定では実行しないので、何も掛からない。
- **どの要件にも対応しない実装が、テストさえあれば見つからない。** 以前の C19・C27 は、実現単位の置き場のコードに、要件を指す印を求めていた。今は、`tests.dirs` の外の、`@covers` を持たないテスト（技術部品の自己検査など）から実行されていれば、実行の記録の検査は通る。記録が仕様のテストだけから作られたかは、見ていない。
- **機能の仕様ではない入口にも、契約を書く手間が要る。** 生存確認や静的なファイルの配信にも、UC・REQ・テスト・契約の操作・実例・アダプターの対応が要る。数行の入口に対して、書くものが多い。契約の外の入口を 1 つも認めないことと引き換えである。
- **契約にある入口が、必ず実例で実行されるわけではない。** `owned: false` の inbound の操作（外部サービスからの通知など）は、fixed の契約なら入口は E1 を通り、実例も必須だが、contract-run は既定では実例を実行しない。draft の契約の操作は、E1 が突き合わせ先に数えないので、これには当たらない。
- **契約が fixed でない間は、その契約の入口があると完了の判定が通らない。** 契約が draft の間に入口を先に置いた場合と、fixed の契約を改訂のために draft に戻した場合（入口は実装済み）のどちらも、人間が再び承認して fixed にするまで E1 で失敗する。
- **関数を持たないファイルは、`FNF:0` の行で見分けている。** 関数を持たないファイルに `FNF:0` を書かない道具では、そのファイルも V7 の違反になる。道具が出した記録に `FNF:0` を後から書き足すことは勧めない（関数の情報が落ちたファイルが、関数を持たないファイルに見えて通る）。`FNF:0` の行が道具の出したものかどうかは、機械では確かめていない。
- **`coverage.scope` を狭く書けば、義務（C26）を満たしたまま、確かめる範囲を小さくできる。** 範囲の外のソースの件数は毎回表示するが、外した理由は求めていない。
- **DB で守る規則のテストを `commands.extra` に入れると、`harness verify --level fast`（Stop フック、CI）のたびに実 DB が要る。** `commands.extra` は level `fast` で実行するためである。
- **fixed の契約に inbound の操作が 1 つも無い間は、`commands.list_entries` を none にでき、その間は入口があっても見ない。** 0 行の一覧が通る条件と同じにした。入口だけを先に書いて、契約を 1 つも fixed にしなければ、検査の外に置ける（inbound の操作を持つ契約を 1 つ fixed にした時点で、none は通らなくなる）。
- **一覧のパスの書式が狭い。** パラメーターは `:name` と `{name}`、何でも受ける部分は `*` だけなので、枠組みがそれ以外の形で登録を持つ場合は、一覧を出すスクリプトが直して出す。直し方が正しいか（catch-all を `*` で出しているか）は、機械では確かめていない。区分の一部だけがパラメーターの形（`/files/{name}.json`、`/items/{id}:cancel`、`/@{user}`）は書けないので、区分の全体をパラメーターにして、契約も入口も書き直す（`/files/{name}`、`/items/{id}/cancel`、`/users/{user}`）。外から決められた URL をこの形で受ける入口は、置けない。契約の `wire.path` は、spec-lint が同じ読み方（`tools/_shared/entry-path.mjs`）で draft の段階から検査する。
- **pipefail に対応していないシェルでは、入口の一覧のコマンド `a | b` の左側の失敗を見逃す。** fixed の契約に inbound の操作があるときに限り、空の一覧と、fixed の操作の入口が欠けた一覧は、E4・E2 が見つける。
- **入口の一覧は、利用プロジェクトのコマンドの正しさに依る。** コマンドが載せ忘れた入口は見つからない。本番と同じ組み立てから列挙する形にすることを文書で求めているが、機械では確かめていない。一覧を出すコマンドを書いて保つ手間が、利用プロジェクトに生じる。
- **実行の記録が示すのは、名前のある関数が 1 回でも呼ばれたかどうかまでである。** 無名の関数の中だけにある処理は見ない。変数に入れた関数式に名前を付けない道具もあり、その道具では対象が減る。同じ名前の関数が 1 つのファイルに複数あると、どれか 1 つが呼ばれていれば通る。行と分岐は見ない。
- **`coverage` を none にできるプロジェクトが、まだ残る。** active な REQ が 1 つも無い間と、`source` が none の間は、`coverage` を none にできる（義務が無い）。`source` を none にすること自体は、active な REQ があれば C26 が止める。義務にしたことで、版を上げた利用プロジェクトは、テストのコマンドが実行の記録を書き出すように整えるまで、完了の判定が失敗する。記録を取る分、テストの時間も増える。
- **実装が残る draft の REQ に、テストを求めなくなった**（C1 の後半）。実装の印を読まないので、どの REQ の実装が残っているかを機械が知る手段が無い。テストの無いコードは、実行の記録の検査が見つける。
- **版を上げた利用プロジェクトは、手で移行する。** 廃止したキーを消し、`commands.list_entries` を宣言し、DB で守る規則にテストを書き、呼ばれていない関数を片付ける（消す、テストを足す、理由を書いて認める）。済むまで、完了の判定は失敗する。手順は `docs/apm.md`。
- `harness lint entry`（テストの入口）と `harness lint entries`（入口の一覧）、設定の `entry` と `commands.list_entries` は、名前が似ている。前者は ADR-0066 で決めた名前で、変えていない。

## 却下した選択肢

- **`@implements` を残し、書く量だけを減らす（ファイルの単位にする、UC だけを指す、など）**: 書けば通ることは変わらない。粗くするほど、何も示さなくなる。裏付けは実行の記録が持つ。
- **`@operation` を残し、入口の一覧と併用する**: 入口と操作の対応は、一覧の method・パス・entry と契約で決まる。同じ対応を注釈でも書かせると、2 つが食い違ったときの正が決まらない。
- **入口を、これまでどおりソースの行の正規表現で探す（`entry_pattern` を残す）**: 正規表現が拾えない書き方の入口が、検査から黙って外れる。接頭辞が分からないので、パスを完全には比べられない。アプリ自身に列挙させれば、登録されたものがそのまま出る。
- **harness が、フレームワークごとの入口の列挙を持つ**: harness がフレームワークの内部を知ることになる（共有の harness にホスト固有の事実を置かない、という不変条件に反する）。一覧の形だけを決め、出し方は利用プロジェクトのコマンドに任せる。
- **exec-check が、一覧を出すコマンドを自分で実行する**: 読むだけの検査と、利用プロジェクトのコマンドを実行する検査が混ざり、level `lint` で何が実行されるかが分かりにくくなる。実行は検査の並びの 1 か所に置く（ADR-0065、ADR-0066）。
- **DB で守る規則を、スキーマの制約の注釈（`@implements BR-nnn`）で確かめ続ける**: 注釈は、制約が規則を守ることを示さない。断られることを確かめるテストのほうが強い。「どの規則にも対応しない制約」の検出は失うが、その検出のためだけに、制約を探す正規表現と注釈を保つことはしない。
- **どの規則にも対応しない DB の制約を、今回、別の方法で検出する**: スキーマの制約を言語によらず列挙する手段が要る。今回の範囲に入れない。
- **名前の無い関数を、行の位置で指して認められるようにする**: 行の位置は編集のたびにずれ、認めた項目が別の関数を指すようになる。囲んでいる名前のある関数で代表させる案は、lcov の記録が多くの道具で関数の開始行しか持たず、囲みの関係を取れないので採らない。対象から外し、見ないことを代償に書く。
- **関数ごとの情報が無い記録を、ファイルの単位の検査だけで通す**: 関数の単位まで確かめたように見えて、確かめていない。使わないなら、理由を書いて宣言させる。
- **廃止したキーを、黙って読み飛ばす**: 利用プロジェクトは、もう検査されていない注釈と設定を保ち続ける。残っていたら、代わりにすることを添えて失敗にする。
- **廃止した検査の番号を詰める（C1〜C21 に振り直す）**: 過去の ADR、コミット、利用プロジェクトの記録が指す番号と食い違う。欠番にする。
- **契約の外の入口を、理由付きの宣言で認める（`entries.outside_contract`）**: 当初の案。宣言した入口は、契約に無く、テストも求められず、処理が無名の関数なら関数の単位の検査にも掛からない。設定に 1 行足せば、仕様にもテストにも無い入口を置ける。理由を書かせても、入口の中身は誰も確かめない。生存確認のような入口も、契約に書けば、実例で実行され、REQ とテストが付く。
- **一部だけを置き換える過去の ADR（ADR-0055、ADR-0056、ADR-0066）の status も superseded にする**: 一部だけを置き換えるので、全体を置き換えたことにはできない。置き換えた部分をこの ADR に書き、status は変えない。全体を置き換える ADR-0019 だけを superseded にした。
- **`coverage` を、これまでどおり省略も none も認める**: 実装の印を外した後は、実装との対応を確かめる検査が実行の記録だけになる。none を認めると、要件があるのに、その検査が 0 のプロジェクトができる。
- **`entry`（テストの入口が本番の組み立てを通ること）も義務にする**: 本番の組み立てとテストの入口が分かれないスタック（コマンドとして起動される道具など）がある。none の理由を書かせるだけにする。
- **何でも受ける登録の `*` を、パラメーター 1 つと同じに扱う**: `/x/*` の入口が、契約の `/x/{id}` に合ったことになり、契約より広い入口が通る。
