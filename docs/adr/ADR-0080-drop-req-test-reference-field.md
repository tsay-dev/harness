# ADR-0080 要件の検証方針から「参照先」の欄を外し、どのテストが確かめるかは harness index が出す

## Context

UC のひな形（`templates/develop/UC.md`）の要件の小節には、検証方針の最後に「参照先」の欄（`- **参照先**: <tests/ファイル>::<クラスまたは describe>`）があり、REQ ごとに、それを確かめるテストのファイルを手で書かせていた。

同じ事実は、テストの `@covers REQ-nnn#class` にすでにある。lint refs（C1・C3・C10・C11）が読むのは注釈のほうで、「参照先」の中身はどの検査も見ていない。REQ を足すたびに 1 行書く手間がかかるうえ、テストのファイルを移したり名前を変えたりしても、古いパスのまま何も落ちない。mg-pf では 1,144 行あり、あるユニットでは 399 件のうち 30 件が、もう無いテストのファイルを指していた。REQ ごとのテストのファイルの一覧は、`harness index` が注釈から組み立てて出している（`tests:` の行）。

## Decision

1. **ひな形の検証方針から「参照先」の欄を外す。** ひな形の案内のコメントに、どのテストが確かめるかは `harness index` がテストの `@covers` から出すので書かない、と 1 文で書く。docs の規約（`docs.instructions.md` の R-602）にも同じことを 1 文で足す。lint spec は「参照先」を必須の項目として求めていなかったので、必須の項目の変更は無い。
2. **残っている「参照先」は lint spec の警告（warn）にする。** REQ の検証方針に `- **参照先**:` の行があれば、「どのテストが確かめるかは `harness index` が出す。この欄は消してよい」と案内する。違反（err）にはせず、黙って許すこともしない。検査の場所は lint spec の REQ の検査（`validateReq`）の 1 か所。
3. **既存の行を消す道具は作らない。** 利用プロジェクトは、警告を見て手で（または一括の置換で）消す。

強制は lint spec の警告による。警告は終了コードを変えないので、消すかどうかは利用プロジェクトの判断に残る（説得による統制、R-901）。

## Consequences

- REQ を足すときに書く欄が 1 つ減り、テストのファイルを動かしても文書を直す必要がなくなる。どのテストが確かめるかの正本は、テストの注釈の 1 か所になる（R-101）。
- 利用プロジェクトが版を上げると、「参照先」を残した REQ の数だけ lint spec の警告が出る。mg-pf では千件を超え、ほかの警告が埋もれやすくなる。消し終えるまでは、警告の一覧を読む手間が増える。
- 警告に留めるので、消さずに放っておいても CI は落ちない。古い参照先が残り続ける可能性は残る。
- `harness index` を実行しないと、REQ からテストのファイルを引けない。文書だけを読む人には、対応が見えにくくなる。

## 却下した選択肢

- **残っていれば違反（err）にする**: 利用プロジェクトが次に版を上げたとき、千件を超える行で一斉に落ちる。消すだけの機械的な作業のために、ほかの変更の検証が止まる。
- **欄を外すだけで、残っていても何も言わない**: 古いパスを指す行が、正しいもののように残り続ける。外した理由も、代わりに何を見ればよいかも伝わらない。
- **欄を残し、参照先のファイルが実在するかを検査する**: 注釈と同じ事実を 2 か所に持つことは変わらず、検査を 1 つ増やして 2 か所目を守ることになる。
- **一括で消す道具（migrate）を作る**: 消すのは行の削除だけで、置換で足りる。道具とそのテストを持ち続ける費用に見合わない。
