# ADR-0068 レビューの指摘を保留の一覧に書くのをやめ、機械検査にするか、人間に聞いて決める

## Context

レビュー担当（reviewer）の指摘は 2 段だった。機械検査にできる反例を伴うものは `阻止`、それ以外はすべて `持ち越し` で、`持ち越し` は保留の一覧（`docs/verification/DEFERRED.md`）に 1 行ずつ書き、スライスは完了にできた。

- 一覧が減らない。利用プロジェクトの 1 つでは、5 つのユニットで合計 662 件が残っている。「30 日を超えたら昇格か解消かを決める」「同じ対象に 3 件積もったら機械検査の候補」という警告は出ているが、警告は完了を止めないので、行は積もる一方になった。
- 一覧に書けば完了にできるので、仕様が答えを決めていない点（どちらの結果が正しいかを人間が決める必要がある点）も、文言の好みも、同じ「持ち越し」として積まれた。本当に決める必要がある点が、一覧の中に埋もれている。
- 「未決を持ち越さない」「人間は、仕様の確認と、AI が判断できない点の承認だけを行う」という方針と合わない。未決の点は、その場で人間に聞けば未決でなくなる。

## Decision

- レビューの指摘を 2 種類だけにする。
  - `阻止`: 機械検査にできる具体的な反例を伴うもの（これまでと同じ）。テストのクラスか lint の規則にして、機械の検査へ戻す。
  - `問い`: 反例は作れないが、仕様が答えを決めていない点。具体的な入力、2 つ以上の候補、候補ごとの帰結を書く。
- どちらでもない指摘（文言、スタイル、テストや例で決まる境界）は、報告しない。
- `問い` は、そのスライスの中で人間に聞いて決める。答えは仕様（UC・REQ・BR・契約。持続する判断なら ADR）に書き、機械の検査へ戻す。
- スライスの完了の条件を、「`阻止` がゼロで、すべての `問い` に人間が答えている」にする。`問い` が残っている間は、人間待ちである。
- 保留の一覧には、新しい行を足さない。オーケストレーターが `DEFERRED.md` に行うのは、解消した行を消すことだけである。
- 既存の一覧は凍結する。frontmatter に `frozen_at`（凍結した日）を書かせ、その日より後の起票日の行があれば spec-lint が失敗する。`frozen_at` が無い一覧も失敗する。
- 凍結を外す書き込み（一覧を新しく作る、`frozen_at` を変える、行を足す）は、書き込み前の関門（gate-hook）が人間の承認に回す（`ask` / `deferred`）。行を消すだけの書き込みは止めない。
- 残っている行は、そのまま残してよい。解消したら消す。spec-lint は、残っている件数を毎回 1 行で表示する。行ごとの古さと、同じ対象への積もり方の警告はやめる（凍結した一覧は、すべての行が古くなる）。
- 稼働している環境での実行が要る疑念は、指摘にしない。レビュー担当が検査台帳に「`/attack` 向けの疑念」として書き、オーケストレーターが完了の報告で人間に伝える。攻撃を実行するかどうかは、人間が決める。
- 強制の所在: `tools/spec-lint/test/spec-lint.test.mjs` が、`frozen_at` より後の行・`frozen_at` の欠落を失敗にすることと、件数の表示を確かめる。`tools/gate-hook/test/gate-hook.test.mjs` が、凍結を外す書き込みを承認に回すことを確かめる。

## Consequences

**得られるもの**

- 指摘の結末が、「機械の検査になった」「人間が決めて仕様に書いた」「報告しない」のどれかに決まる。完了したスライスに、未決の点が残らない。
- 人間に届くのは、決める必要がある点だけになる。候補と帰結が付いているので、選ぶだけで済む。
- 保留の一覧に行を足すには、人間の承認が要る（関門を有効にしているプロジェクト）。関門が無くても、凍結した日より後の起票日の行は検査で失敗する。

**代償と今後の制約**

- 人間に聞く回数が増える。これまで一覧に積んで先へ進めていた点で、スライスが人間待ちになる。
- 文言やスタイルの指摘は、どこにも残らなくなる。直す価値があるものは、lint の規則にするか、人間がレビューで拾う。
- 既存の一覧の行（利用プロジェクトの 1 つで 662 件）は、この変更では減らない。対象のファイルを触るときに、順に片付ける。片付ける順番や期限は決めていない。
- 関門（gate-hook）を有効にしていないプロジェクトでは、`frozen_at` を書き換えるか、起票日を偽れば、行を足して検査を通せる。spec-lint だけでは、これを止められない。関門を有効にしていても、エディター以外の経路（シェルのコマンドなど）での書き換えは止めない。手順から「保留に書く」を外したことと合わせて防ぐ。
- 既にある行の ID を使い回して中身を別の指摘に書き換える、1 つの行に 2 件目を詰める、表の外に文章で書く、という足し方は、関門も spec-lint も見分けない。
- 凍結済みの一覧にある指摘は、レビュー担当が再び報告しない（反例を得て `阻止` にできるときを除く）。触っているスライスに関わる行でも、`問い` としては出てこない。「未決の点が残らない」は、新しく見つかった点についてだけ成り立つ。
- 利用プロジェクトは、版を上げるときに、既存の `DEFERRED.md` に `frozen_at` を足す必要がある。足さないと spec-lint が失敗する。
- `問い` と「報告しない指摘」の境目は、レビュー担当の判断に依る。仕様の答えが決まっていない点を「スタイル」と見なして報告しないと、未決の点が見えなくなる。これを機械では確かめていない。

## 却下した選択肢

- **既存の一覧も取り下げる（ファイルを消す）**: 反例つきの指摘が含まれていて、どのソースからも作り直せない。消すかどうかは、行ごとに人間が決めることである。
- **既存の行をすべて仕分けてから凍結する**: 数百件の仕分けに時間がかかり、人間の判断が要る件数も、やってみないと分からない。新しく足すのを止めることを先に行う。
- **警告を失敗に変える（30 日を超えた行で完了を止める）**: 期限が来るたびに、行を直す代わりに日付を書き換える動機が生まれる。足させないほうが単純である。
- **`問い` を別の一覧に書いてスライスを完了にする**: 名前を変えた保留の一覧になる。完了の前に人間が答える形にする。
