# ADR-0038 進捗は保存せず、active な GOAL の成立状態を終端リストの結果と trace-check の違反から導出する

## Context

複数のホストを並行して進めると、「このプロジェクトは今どこまで出来ているか」が AI との会話の中にしか残らず、人は毎回 AI に尋ねることになる。知りたいのは作業の量（コミット数・消化したタスク数）ではなく、目指す状態に対して今なにが成り立っているかである。

harness には工程状態として `UC.md` の `phase:` があるが、これは orchestrator が進める欄で、機械が確かめた事実ではない。導入済みのホストを調べると、UC の大半が `phase: 完了` である一方で、`DEFERRED.md` に 100 件を超える保留が残り、baseline には被覆するテストの無い REQ が数十件載っていた。`phase:` を数えても、成り立っているかどうかは分からない。

進捗をホストの外（サーバーや管理ツール）に持つと、SSOT がプロジェクトの外に出る。ホストの docs には人間ゲートを通った GOAL / UC / REQ が既にあり、`@covers` / `@implements` / `@scenario` でテストと実装に繋がっている。足りないのは、それを GOAL の単位で読める形にする導出だけである。

なお、`trace-check` は `process.exit()` で終わるため、stdout がパイプのとき出力が 64KB で切れていた。大きなホストではレポート末尾の FAIL 一覧が `stop-gate` の差し戻しに載らない。機械可読な出力を足すには、これを先に直す必要があった。

## Decision

- **進捗は保存しない。** GOAL ごとの成立状態を `tools/goal-status` がその都度導出し、ファイルを書かず、コミットもしない（R-1003 の適用）。報告には観測時刻・コミット・未コミットの件数を必ず添える。
- **分母は人が決める。** 対象は `status: active` の GOAL だけ。backlog からの昇格と `active` 化は人間ゲートなので、AI の書いたものが分母を増減させない。`withdrawn` と backlog の `planned` は数えない。
- **分子は機械が決める。** 状態は 3 値の閉じた語彙で、次の順に決める。
  1. `unobserved`（`no-conditions`）: 配下に `active` な REQ が無い。UC を 1 つも持たない GOAL もここに入り、`true` にはならない。
  2. `false`: GOAL・配下の UC・配下の REQ を名指しする trace-check の違反がある。**baseline 済みの違反も数える**（baseline は止めないための台帳で、成り立っている証拠ではない）。
  3. `unobserved`（`gate-red`）: 終端リストのどれかが失敗した。
  4. `unobserved`（`not-executed`）: `commands.test` が未宣言、または実行しない指定。
  5. `true`: 上のどれでもない。
- **`phase:` は判定に使わない。** 表示し、`phase: 完了` なのに `false` または `no-conditions` である UC を「申告との食い違い」として数えるだけにする。
- **`DEFERRED.md` は状態を変えない。** 機械判定できない指摘なので、件数を添えるだけにする。
- **goal-status は報告であって、ゲートではない。** 終了コードは状態を表さない（`0` = 報告を出した / `2` = 使い方・設定の誤り）。
- **知識を複製しない。** 木と違反は `trace-check --json` から受け取り、goal-status は docs を解析しない。終端リストの並びは `tools/gate-hook/suite.mjs` に 1 つだけ持ち、`stop-gate` と共有する。違反が名指しする ID は、検査が違反を出す箇所で宣言し、文面から拾い直さない。
- `trace-check` は `process.exit()` をやめ、終了コードを置いて書き切ってから終わる。

強制の所在: 状態と理由の語彙・判定の順序・baseline と未宣言の扱い・終了コードは `tools/goal-status/test/goal-status.test.mjs` の回帰検証、`--json` の形と出力が切れないことは `tools/trace-check/test/trace-check.test.mjs`、終端リストの並びの共有は `stop-gate` と goal-status が同じ `suite.mjs` を import していること自体が担う。「出力をコミットしない」は、ツールがファイルを書かないことと `CLAUDE.md` の不変条件による説得的な統制である（R-901）。

## Consequences

- 人は AI に尋ねずに、GOAL ごとの成立・不成立・未観測と、その理由を読める。未観測の理由は次に動くべき側を示す（条件が未定義なら人、終端リストが赤なら AI、テスト未宣言ならホストの設定）。
- baseline に載せた負債が GOAL の単位で見えるようになる。終端リストが緑でも、未被覆の REQ を持つ GOAL は `false` のままになる。導入直後のホストでは多くの GOAL が `false` と出る。
- **粒度はスイートである。** `commands.test` は 1 行のコマンドで終了コードが 1 つなので、赤のときにどの GOAL のテストが落ちたかは分からない。その間、違反を持たない GOAL はすべて `unobserved` になり、表は「終端リストを緑に戻せ」以上のことを言わない。
- **`commands.test` を宣言していないホストでは `true` が 1 つも出ない。** 宣言するまで、違反の無い GOAL はすべて `unobserved` になる。
- **`true` は「完成の定義を満たした」であって「正しい」ではない。** trace-check の緑が review に残すもの（分割が尽きているか、断言が文の意味を検証しているか）と、`GLOBAL.md` が検証しないと宣言した範囲は、そのまま残る。
- **観測するのは作業ツリーで、`HEAD` ではない。** 未コミットの件数は添えるが、あるコミットの状態を知るには clean な checkout（CI）で走らせる必要がある。その仕組みは今回入れない。
- **GOAL が扱うのは振る舞いだけである。** 公開・デプロイ・KPI はこの報告に現れず、全 GOAL が `true` でもプロジェクトが終わったことは意味しない。harness を導入していないプロジェクトと、開発以外のプロジェクトも対象外である。
- goal-status を走らせるたびに終端リスト全件（ホストのテストを含む）が走る。重いホストでは `--no-run` で違反だけを見る使い方になり、そのとき `true` は出ない。
- `stop-gate` の検査の実行部が `suite.mjs` に移った。`stop-gate` の出力と終了コードは変えていない。

## 却下した選択肢

- **進捗を中央のツール（課題管理・ノート・自作のデータベース）に持つ**: ホストの docs にある GOAL と二重管理になり、必ずずれる。AI はリポジトリの中で働くので、読まれるのは docs の側である。
- **GitHub の Issues / Projects を使う**: タスクの発行と消化の管理になる。知りたいのは状態の一致であって、消化した量ではない。
- **テストを SSOT にして「通った数 / 全テスト」を進捗にする**: テストは AI が書くので、分母を AI が決めることになる。
- **`phase: 完了` の UC を数える**: 申告であって観測ではない。実際に、申告は完了でも被覆の無い REQ と保留が残っていた。
- **「今の目標」を指す文書を docs に 1 枚足す**: `active` な GOAL の集合がそのまま目標であり、未達の GOAL がそのまま差分になる。文書を足すと SSOT が増える。
- **観測を集約側（サーバー）で実行する**: ホストごとのビルド環境（シミュレータなど）を集約側に持つことになり、管理の仕組みそのものが大きな開発になる。観測はホストの環境で走らせ、集約側は結果を読むだけにする。
- **終端リストが緑なら、baseline 済みの違反を持つ GOAL も `true` にする**: baseline は導入時に既存の違反を止めないための台帳である。それを成立の証拠にすると、負債を台帳に載せるだけで進捗が上がる。
- **違反の帰属を、メッセージの文面から ID を正規表現で拾って決める**: 文面を直すと帰属が黙って変わる。検査が違反を出す箇所で ID を宣言する。
- **赤いスイートの失敗を、テスト結果のファイルを読んで GOAL ごとに帰属する**: 結果の形式はテストランナーごとに違い、`commands.test` は 1 行のコマンドとしてしか宣言されていない。形式を推測して読むことになるため、今回は入れない。
- **goal-status を trace-check のモードにする**: trace-check はトレーサビリティだけを検査し、ホストのコマンドを実行しない。成立の判定には実行結果が要るので、別のツールにして、trace-check には事実を出す `--json` だけを足す。
