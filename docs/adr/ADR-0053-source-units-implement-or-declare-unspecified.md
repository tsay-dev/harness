# ADR-0053 宣言した実現単位は @implements か仕様外の印を持ち、どちらも無い単位を trace-check が検出する

## Context

コードと仕様の紐づきは、仕様 → コードの向きだけが機械で検査されていた。C14 は「active な REQ・BR を指す `@implements` が 1 つ以上あるか」を見て、C5 は書かれた注釈の参照先が実在するかを見る。どの仕様も指さない本番コードは、どの検査にも映らない。実装担当が REQ に無い振る舞いを足しても、機械は止めない。

テスト側には同じ穴に対する仕組みがすでにある。`tests.test_pattern` でテスト関数の印を宣言すると、C11 が `@covers` の無いテストを報告し、`tests.exempt_pattern` の印（`// 仕様外:`）があるものは除外として数える。

一方、本番コードには REQ を持たない技術部品（外部境界のクライアント、設定の読み取りなど）が正当に存在する。その振る舞いの正本は単位の doc comment である（ADR-0051）。すべての単位に `@implements` を求めると、これらが違反になる。

## Decision

- `traceconfig.json` の `source` に、テストと同じ形の 3 つのキーを足す。
  - `unit_pattern`: 実現単位（ユースケースクラス、ルール関数など、`@implements` を付ける単位）の印。一行一正規表現で、捕捉 1 が単位名。
  - `implements_placement`: 注釈の位置（`before` = 単位の直前のコメント、`after` = 単位の行から本体の先頭）。既定は `before`。
  - `exempt_pattern`: 仕様を持たない単位の明示（既定 `// 仕様外: <理由>`）。
- **C19**: `unit_pattern` に一致する単位が、`@implements` も仕様外の印も持たなければ違反にする。`unit_pattern` が未宣言なら判定しない。単位の同一性はファイル + 名前で、baseline のキーは行番号に依存しない。
- C11 の未注釈テストの集計を、テストと実現単位で共通の関数にする（窓の決め方も共通）。
- テストと違い、どの単位の窓にも属さない `@implements` は違反にしない。検査を強制する分岐の中の注釈（comments の規約）は単位の窓の外に出うるため。
- REQ を持たない技術部品には、`@implements` の代わりに仕様外の印を付ける（comments の規約、implementer の不変条件）。
- テンプレートの `traceconfig.json` に TypeScript の既定（`export` された function / class / const）を置く。どの単位を実現単位とみなすかは利用プロジェクトが宣言し、推測しない。
- 強制は trace-check で、develop の完了条件、stop-gate、CI を通じて効く。仕様外の印が正当か（実は REQ にすべき振る舞いではないか）は reviewer の確認で、説得による統制（R-901）。

## Consequences

- 良: 仕様を指さない本番コードが、注釈か仕様外の印のどちらかを持つまで完了判定を通らない。仕様外の単位が数として見え、レポートに内訳が出る。
- 良: テストと本番コードで、注釈忘れの扱いが同じ形になる。
- 悪: 既存の利用プロジェクトが `unit_pattern` を宣言すると、注釈の無い単位が大量に新規違反になる。R-804 に従い、宣言した時点で `--update-baseline` を 1 回だけ使う。
- 悪: 窓は行の位置で決まるので、単位の本体に書いた注釈が次の単位に帰属することがある（`before` の場合）。その単位は注釈済みに見え、見逃しになる。粒度の正しさは reviewer に残る。
- 悪: `unit_pattern` が拾わない書き方（`export` されない関数、別の構文）の単位は検査されない。どこまでを実現単位とするかは利用プロジェクトの宣言に依存する。
- 悪: 仕様外の印は理由を書けば何にでも付けられる。印の乱用は機械では止まらない。

## 却下した選択肢

- **ファイルごとに `@implements` か仕様外の印を 1 つ以上求める**: 設定は不要だが、1 ファイルに注釈が 1 つあれば残りの単位を見ない。仕様を指さない関数が同じファイルに足されても検出できない。
- **違反にせずレポートに一覧を出すだけにする**: CI を落とさない仕組みは、完了条件に効かない。テストの C11 と扱いを揃える。
- **すべての単位に `@implements` を求め、例外を認めない**: REQ を持たない技術部品（ADR-0051）が違反になる。REQ は外から観測できる振る舞いだけを持つ（R-401）ので、技術部品のために REQ を作ることもできない。
- **言語ごとの構文解析で単位を特定する**: harness の検査は言語に依存しない行単位の正規表現で動く（注釈の検出と同じ）。構文解析を持つと、対応する言語ごとに実装が要る。
- **帰属なしの `@implements` もテストと同じく違反にする**: 検査を強制する分岐の中の注釈が、最後の単位の後ろに来ると誤検出になる。
