# ADR-0044 プロンプトは到達状態と不変条件だけを持ち、手順と機械が検査できる事項は削る

## Context

ADR-0033 は「最終的に仕様と実装が紐づいていればよく、その間のプロセスは問わない」を原理として採り、`develop/SKILL.md` を 443 行から 66 行に縮めた。しかし手順は削除されず `references/` に移った。`playbook.md` は 179 行で、受領時の処理表 17 行、並行条件 4 項、プロバイダー別の起動手順を持つ。agent 本文は 49–86 行で、`spec-author` の決定基準表と「入れないもの」表は `templates/develop/` のひな形コメントと `docs.instructions.md` §3 を、`test-author` の分割クラス節は同 §11 を、それぞれ言い換えて重複している。`develop-core` のプロンプト正本は合計 1,235 行、`rules-*` は 6,822 行で、本文を再掲するチェックリスト見出しが 30、公開フレームワークの NG / OK コード例が 36、「日本語で書く」の繰り返しが 43 箇所ある。

利用者の前提は次のとおり。モデルの進歩に伴い、具体的な手順を与えるより、到達すべき状態を厳格に定義して到達方法をモデルに任せる方が効率がよい。脱線防止のための厳格な手順は、モデルが本来発揮できる性能の上限にもなる。この repository の履歴はこれを裏付ける。判定ループの非収束（ADR-0031）、並列生成のドリフト（ADR-0011）、注釈忘れ（ADR-0019）はいずれも散文の追加ではなく、機械検査と閉じた語彙の追加で解決した。

利用者が提案した到達状態は「仕様と実装が明確に紐づくこと」である。これは必要だが十分ではない。紐づきは注釈 1 行で成立し（C14 は無関係な関数への `@implements` でも通る、ADR-0019）、仕様・実装・テストを同じ主体が書けば、すべて紐づいていてすべて誤っている状態が作れる。紐づきが意味を持つのは、仕様が人間の承認を経ており、検証が実装から独立に導出され、完了の判定が閉じている場合だけである。

`CLAUDE.md` §0 は既に「手順を追加する前に機械チェックを追加する」「厳守事項と柔軟な事項を分ける」を定めるが、プロンプトの各行を残すか削るかの判定基準と、到達状態そのものの定義を 1 箇所に持っていない。

## Decision

- **到達状態を 1 文で定める。** 「人間が承認した仕様から、実装とその検証が互いに独立に導出され、両者の紐づきを機械が検査して完了を判定できる状態」。4 つの性質に分解する。
  1. **仕様は人間が承認した 1 箇所にある。** `docs/` の SSOT は人間ゲートで `active` になり、コードは正本にならない（R-801）。人間ゲートは SSOT、見た目、DB スキーマの 3 つだけ。
  2. **検証は実装から独立に導出されている。** テストは REQ / 契約 / UC から実装を読まずに書かれ、reviewer は作成者と別コンテキストで、契約の例は実装に対して実行される。作成者 ≠ 判定者。
  3. **紐づきは機械で検査できる。** REQ → 分割クラス → テスト、REQ / BR → `@implements`、契約 → 例 → 実装、UC → シナリオテストの各辺を spec-lint、trace-check、contract-run、typecheck / lint / test / system が判定する。
  4. **完了は閉じたリストで判定される。** 終端リストがすべて exit 0 で reviewer の `阻止` がゼロのときだけ完了。それ以外の「完了」はない。
- **プロンプトの各行の残置基準。** `SKILL.md`、`references/`、agent、instruction の行は、次のいずれかに該当するときだけ残す。(a) 到達状態または不変条件（最後に成り立つべきこと、決して起きてはならないこと）。(b) 入出力契約（agent が受け取るもの・返すものの形）。(c) 機械が検査せず、かつモデルが自力では到達しない知識（operation → entry 規約、ロケーター導出規約、閉じた語彙、crow のような非公開フレームワークの事実）。
- **削るもの。** 手順の順序・回数・タイミング。機械が検査する事項の再説明（検査器の失敗出力が指示であり、コマンド名だけ残す）。`templates/`、`docs.instructions.md`、tool README と重複する表。理由と背景（ADR に置く）。本文を再掲するチェックリスト。公開フレームワークの一般知識と NG / OK 例。プロバイダー固有の起動手順（アダプターの出力または `tools/<provider>-sync` の README へ）。各ファイルで繰り返す「言語」ブロック（言語方針は `CLAUDE.md` と orchestrator の Task 入力が担う）。
- **知識の唯一の置き場。** 到達状態と不変条件は `develop/SKILL.md`。入出力契約は各 agent。書式は `templates/`。規則 ID（R-nnn）は `docs.instructions.md` に 1 行ずつ、機械が検査するものは検査器名だけを添える。作成者間の調整契約（operation → entry、スイート分離、識別子属性）は `rules-*` の末端ファイル。手順の置き場は作らない。`playbook.md` は削除候補、`commit.md` / `adr.md` はガードレールと書式 SSOT だけを残す。
- **適用順。** `develop-core`（SKILL、references、agent、instruction）→ `rules-*`（公開フレームワークは一般知識を削る。crow はフレームワークの事実を残し手順を削る）→ `produce-video` / `render-media` / `translate-manga`。各段で生成物を再生成し、`test_projection.py`、spec-lint、各 tool のテストを緑に保つ。
- **強制の所在。** ファイル種別ごとの行数上限を `tools/apm/test_projection.py` に固定する（説得的な「約 100 行」を構造的にする）。上限値は最初の削減で確定し、以後は baseline と同じく縮む方向にだけ動かす。削除する「禁止」のうち機械で検査できるものは、削除と同じ変更で lint または hook へ移す。効果は利用プロジェクトの `gate-log.mjs --summary` の阻止件数で観測し、非収束が出た場合は散文全体ではなく該当する 1 行だけを戻す。

## Consequences

- 良: 起動ごとのコンテキストが縮み、分解と順序はモデルが決める。各知識の置き場が 1 つになり、重複した表の乖離が消える。機械検査の失敗が唯一の矯正経路になり、何が効いているかをログで測れる。
- 良: 到達状態が 1 文で言えるため、新しい規則を足すときに「状態か手順か」を即座に判定できる。
- 悪: 散文が止めていた逸脱は、当初は stop-gate や trace-check の阻止として表に出る。往復が一時的に増える。
- 悪: 機械検査のない失敗様式（テストの弱体化、意味のずれ、DOM 依存のロケーター）は reviewer と人間ゲートへの依存が強まる。reviewer の観点表は craft として残さざるを得ない。
- 悪: `rules-crow` は「モデルが知っている」を理由に削れないため、総行数の削減幅は限定的である。
- 悪: 削った行が過去の事故の再発防止だった場合に気づきにくい。ADR を引用する規則は削除前に当該 ADR を読み、R-ID の語彙は残す。
- 悪: 行数上限は分割を誘発し得る。上限は目安ではなくラチェットなので、超えたら削る側で解く。
- パッケージングの検証は実際のプロバイダーセッションの代わりにならない。削減後の挙動は利用プロジェクトでの実走で観測する。

## 却下した選択肢

- **現状維持（手順で統制する）**: 利用者の前提に反する。履歴上、効いたのは散文ではなく機械検査と閉じた語彙だった。
- **手順を `references/` に移すだけ（ADR-0033 の方式を続ける）**: references は「最初の起動前に読む」とされ、毎回読まれる。置き場が変わっただけで拘束は残り、179 行に再成長した。
- **プロンプトを全廃し `CLAUDE.md` と tools だけにする**: 「実装を読まない」「作成者 ≠ 判定者」のように機械が検査できない不変条件に置き場が要る。別コンテキストには agent 定義が、`applyTo` 配送には末端ファイルが要る。
- **到達状態を「仕様と実装が紐づくこと」の 1 性質だけにする**: 注釈 1 行で成立し、自己承認と自己検証を排除できない。人間の承認、独立した導出、閉じた完了判定を欠くと紐づきは形式に留まる。
- **短い要約を `AGENTS.md` に compile して常駐させる**: 常駐ゼロ（`CLAUDE.md` §0）に反する。
- **`rules-*` も一律に「モデルが知っている」として削る**: crow は公開フレームワークではなく、operation → entry などは知識ではなく作成者間の調整契約である。公開フレームワークの一般知識だけを削る。
- **行数上限を説得的な指針のまま残す**: ADR-0033 がそうしたが、手順が references に再成長した。構造的な上限にする。
