# ADR-0056 docs と実装の紐づきに例外を作らず、baseline と黙った省略を廃止し、対象の不在は traceconfig に理由付きで宣言する

## Context

harness は「docs を正本にし、実装とテストを ID で紐づけ、紐づきを機械が検査する」ことで、AI の確率的なミスを補正する。紐づきの正しさ（注釈した単位が本当に文を実現するか）は reviewer が担うが、紐づきがあるかどうかは機械で数えられる事実であり、人の裁量に任せる部分は無い。

ADR-0052〜0055 で未検査の線を塞いだ後も、紐づきをすり抜ける経路が残っていた。

- **撤回済みの仕様への参照が通る。** C3・C5・C15・C16・C17・C20 は「ID が定義されているか」だけを見ていて、撤回済み（withdrawn）も定義済みと数えた。撤回した REQ を実装するコードやテストが残っても通る。
- **契約に無い境界が見つからない。** contract-run は宣言済みの実例を流すだけで、実装にあって契約に無い入口は誰も見ていない。
- **片方向だけの線。** 注釈の無いシナリオテスト、REQ から辿れない BR（テストで検証されない）、注釈の無い DB 制約、どこでも使われない共有エラーコード、用語集のコード識別子とコードの照合が、どれも検査されていない。
- **注釈の窓が広い。** 注釈の帰属を「前の単位の後から次の単位まで」で決めていたので、別の単位の本体に書いた注釈が隣の単位の紐づきとして数えられた。
- **黙った省略。** trace-check は設定キーが無い検査を黙って省き、省いたことを表示しなかった。stop-gate と CI は traceconfig.json が無ければ trace-check を飛ばし、contract-run はアダプターが無ければ、また skip を返した実例があっても exit 0 にした。
- **例外の台帳。** baseline（ADR-0005）は既知の違反を通す。`contract.exclude_codes` は指定したエラーコードを C7 から外す。

## Decision

紐づきに例外を作らない。すり抜けを許す経路はすべて違反か設定エラーにし、「対象がそもそも無い」ことだけを、理由付きの宣言として 1 か所に置く。

- **baseline を廃止する。** spec-lint と trace-check から `--update-baseline` / `--strict` / `--baseline` と台帳の処理を削除し、違反はすべて失敗にする。廃止したフラグと `baseline_file` キーは使い方・設定エラー、残った台帳ファイルは読まずに警告する。R-804 を「紐づきに例外を作らない」に改める。
- **宣言を必須にする。** 紐づきの検査に要るキー（`docs.actors` / `vision` / `glossary` / `shared`、`source` とその `unit_dirs` / `unit_pattern` / `entry_pattern`、`tests` とその `test_pattern` / `system` / `system.test_pattern`、`schema` とその `constraint_pattern`、`contract`）は省略できない。対象が無いなら `{ "none": "<理由>" }` と宣言し、trace-check はその範囲を検査せず、レポートに理由を出す。省略と不在を区別するのは、契約の `auth: none` / `operations: {}`（R-1206）と同じ考え方。
- **黙って省かない。** stop-gate と CI（spec-gate.yml）は traceconfig.json が無ければ失敗にする。contract-run は、実行する実例があるのにアダプターが無ければ失敗、skip を返した実例も失敗にする。
- **撤回済みの仕様への参照を違反にする**（C3・C5・C15・C16・C17・C20）。
- **新しい検査**:
  - C15 の派生: `tests.system.test_pattern` に一致する全テストに `@scenario` を求める。
  - C21: 境界の入口（`source.entry_pattern`）はすべて `@operation UC-nnn#name` を持ち、`@operation` は撤回されていない UC の契約に実在する操作を指し、fixed 契約の全操作はソースのどこかの `@operation` から指される。
  - C22: active な BR は active な REQ の `br:` から参照される（規則を検証するテストに辿れる）。
  - C23: スキーマの制約（`schema.constraint_pattern`）はすべて `@implements` を持つ。
  - C24: 共有語彙の全エラーコードは、撤回されていない UC のどれかの契約の `errors` で使われる。
  - C25: living の用語集のコード識別子は、ソース（とスキーマ）に存在する。
  - 宣言した共有語彙・用語集のファイルが無いことも違反にする。
- **注釈の窓を絞る。** `before` は単位の印の行と、その直上に連続する行（空行か別の単位の印で切れる）、`after` は単位の印の行と次の行だけを見る。
- **`contract.exclude_codes` を廃止する。** 契約に無いエラーコードは `error_code_pattern` に一致させない。
- 層の向き（`layering`、C6）は紐づきではないので、必須にしない。

## Consequences

- 良: 検査が通れば、宣言した範囲では docs と実装・テストの紐づきに抜けが無い。検査しない範囲は、traceconfig.json の none 宣言とレポートにすべて現れる。
- 良: 撤回した仕様に紐づくコードとテストが、撤回と同じ変更で片付く。
- 良: 実装にあって契約に無い入口、テストに辿れない BR、注釈の無い DB 制約が見つかる。
- 悪（破壊的変更）: 既存の利用プロジェクトは、harness を上げると次のどれかで止まる。traceconfig.json の宣言不足（設定エラー）、baseline に頼っていた既知の違反、`--strict` / `--update-baseline` の呼び出し、`contract.exclude_codes`、skip を返す契約アダプター。
- 悪: 既存プロジェクトへの導入は、違反ゼロを保ったまま宣言の範囲を広げて進めるしかない。docs-migrate は、紐づきが揃うまで文書を draft に留め、注釈の揃った範囲だけを `tests.dirs` / `source.unit_dirs` に入れる形に変わる。
- 悪: 実機・シミュレーターでしか到達できない操作（skip を返していたもの）も、契約アダプターから実行できるようにする必要がある。
- 悪: none の宣言は理由を書けば通る。ただし 1 か所にまとまり、差分とレポートに必ず現れるので、レビューで見落とさない。
- 悪: `entry_pattern`・`constraint_pattern`・用語集の照合は行単位の正規表現で、書き方によっては拾えない入口・制約・識別子がある。何を拾うかは利用プロジェクトの宣言に依存する。用語集の照合は識別子の存在だけを見て、それが用語の意味で使われているかは見ない。
- 悪: 窓を絞ったので、doc comment と単位の間に空行を挟んでいた既存のコードは、注釈の位置を直す必要がある。
- 悪: CI（spec-gate.yml）は利用プロジェクトのツールチェーンを持たないので、contract-run を実行しない。契約の実行は stop-gate と、利用プロジェクト自身の CI に残る。

## 却下した選択肢

- **baseline を移行専用に限定して残す**（触ったファイルの既知違反は失敗にする）: 例外の範囲は狭まるが、まだ触っていない古いコードには例外が残る。検査が通っても紐づきが揃っているとは言えない。
- **省いた検査を表示するだけにする**: 表示されても通るなら、省略は例外のまま残る。対象が無いことは宣言として明示させ、宣言の無い省略は設定エラーにする。
- **none の宣言を認めず、全キーに実在を求める**: DB を持たないアプリ、入口を持たないライブラリ、ADR だけのリポジトリ（harness 自身）のように、対象が本当に無い場合を表せない。
- **契約に無い入口を、フレームワークごとの命名規則から逆算して見つける**: 規則はフレームワークのパッケージごとに違い、harness の検査が言語やフレームワークに依存する。入口の印は正規表現で宣言させ、紐づけは言語に依存しない注釈（`@operation`）で持つ。
- **BR にも `@covers BR-nnn` を書かせる**: BR は REQ を通じて外から観測できる振る舞いになる（R-401）。REQ の `br:` から辿れれば、REQ のテスト（C1 / C10）が規則を検証する。
- **スキーマの全制約に注釈を求める**: 主キーや外部キーなど、業務ルールでない制約まで BR を要求することになる。どれをルールの制約とみなすかは `constraint_pattern` で宣言させる。
