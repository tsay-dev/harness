# ADR-0055 仕様に紐づける範囲は traceconfig の場所の宣言で決め、コードに書く仕様外の印を廃止する

## Context

ADR-0053 は、宣言した実現単位に `@implements` か仕様外の印（`source.exempt_pattern`、既定 `// 仕様外: <理由>`）を求めた。テスト側にも同じ印（`tests.exempt_pattern`）があり、C11 は印のあるテストを `@covers` の欠落ではなく除外として数えていた。

この印には次の問題がある。

- 印を書くのは実装担当自身で、1 行書けば検査を通る。作った本人が自分の成果物の例外を決める形になり、作成者 ≠ 判定者の原則に反する。
- 理由は自由な文章で、機械は中身を判定できない。REQ にすべき振る舞いを技術部品として逃がしても、reviewer が気づかない限り通る。
- 印は単位ごとに散らばり、数が増えても 1 か所に記録が残らない。仕様外は増え続ける。
- ADR-0051 で技術部品の自己検査は implementer が書くと決めたので、そのテストは REQ を持てず、テスト側でも印が増える。

## Decision

- **コードに書く仕様外の印を廃止する。** `source.exempt_pattern` と `tests.exempt_pattern` を削除し、設定に残っていれば trace-check は設定エラー（exit 2）で止まり、移行を促す。
- **本番コード**: `traceconfig.json` の `source.unit_dirs` に実現単位を置く場所（テンプレートの既定は `src/domain`、`src/usecase`）を宣言する。**C19** は、そこにあり `source.unit_pattern` に一致する単位がすべて `@implements` を持つことを求める。例外は無い。`unit_dirs` 未宣言なら判定しない。宣言したら `unit_pattern` は必須。
- **テスト**: `tests.dirs` は仕様のテストを置く場所の宣言そのものとし、新しいキーは足さない。C11 は `tests.dirs` のテストがすべて `@covers` を持つことを求める（`test_pattern` 宣言時）。
- **REQ を持たない技術部品**（外部境界のクライアント、設定の読み取りなど）は `unit_dirs` の外（infra など）に置き、その自己検査は `tests.dirs` の外に置く（comments の規約、implementer の不変条件）。
- 仕様外を増やす経路は、`traceconfig.json` の場所の宣言を変えるか、コードを宣言の外に置くかの 2 つだけになる。前者は差分の 1 行として、後者は配置の判断としてレビューに見える。
- 強制は trace-check（C11 / C19）で、develop の完了条件、stop-gate、CI を通じて効く。宣言の外に置かれたコードに業務ルールが紛れていないかは reviewer の確認で、説得による統制（R-901）。

## Consequences

- 良: 実装担当が 1 行で例外を作る経路が無くなる。例外の範囲は `traceconfig.json` の 1 か所に集まる。
- 良: 本番コードとテストで「仕様に紐づける範囲は場所で決まる」という同じ考え方になる。テンプレートの `layering`（domain / usecase / infra）とも揃う。
- 良: reviewer が見る対象が「宣言の外に置かれたコード」に絞られる。
- 悪（破壊的変更）: `tests.exempt_pattern` を設定している利用プロジェクトは、harness を上げると trace-check が設定エラーで止まる。印の付いたテストを `tests.dirs` の外へ移すか、REQ に紐づけてからキーを削除する必要がある。
- 悪: 技術部品のテストを `tests.dirs` の外に置くため、テストのディレクトリ構成を変える必要がある利用プロジェクトがある。`commands.test` がそのテストも実行するかは利用プロジェクトの設定に依存する。
- 悪: 業務ルールを infra に置けば C19 を逃れられる。層の向き（C6）は依存の方向を見るだけで、置かれたコードの中身は見ない。
- 悪: `unit_dirs` の中にも、REQ を持たない小さな補助関数を `export` することがある。`unit_pattern` を絞るか、補助関数を外に出す必要がある。

## 却下した選択肢

- **仕様外の印を残し、数をラチェットで増やさない**: 印の数を台帳で縛っても、印を書くのが作った本人である点は変わらない。台帳の更新がもう 1 つの例外の経路になる。
- **仕様外の印に ADR の参照を必須にする**: 技術部品ごとに ADR を書くのは重く、ADR が設計判断ではなく例外の届け出になる。
- **テスト側にも `tests.unit_dirs` などのキーを足す**: `tests.dirs` がすでに「仕様のテストを置く場所」の宣言になっている。キーを増やすと、同じ意味の宣言が 2 つになる。
- **すべての本番コードに `@implements` を求める**: REQ を持たない技術部品（ADR-0051）が違反になる。REQ は外から観測できる振る舞いだけを持つ（R-401）ので、技術部品のために REQ を作ることもできない。
