# ADR-0055 仕様に紐づける範囲は traceconfig の場所の宣言で決め、ソースの全ファイルを実現単位の置き場か技術部品の置き場に分類し、コードに書く仕様外の印を廃止する

## Context

ADR-0053 は、宣言した実現単位に `@implements` か仕様外の印（`source.exempt_pattern`、既定 `// 仕様外: <理由>`）を求めた。テスト側にも同じ印（`tests.exempt_pattern`）があり、C11 は印のあるテストを `@covers` の欠落ではなく除外として数えていた。

この印には次の問題がある。

- 印を書くのは実装担当自身で、1 行書けば検査を通る。作った本人が自分の成果物の例外を決める形になり、作成者 ≠ 判定者の原則に反する。
- 理由は自由な文章で、機械は中身を判定できない。REQ にすべき振る舞いを技術部品として逃がしても、reviewer が気づかない限り通る。
- 印は単位ごとに散らばり、数が増えても 1 か所に記録が残らない。
- ADR-0051 で技術部品の自己検査は implementer が書くと決めたので、そのテストは REQ を持てず、テスト側でも印が増える。

印を廃止して「実現単位を置く場所（`source.unit_dirs`）」だけを宣言する最初の案は、レビューで次の抜けが見つかった。

- `unit_dirs` の外は何も問われないので、新しいディレクトリを作ってコードを置くだけで C19 の外に出る。
- `unit_dirs` の中でも、走査対象の拡張子（`source.extensions`）に無いファイルに単位を置けば走査されない。
- ディレクトリしか書けず、Feature-first の構成（機能ディレクトリに routes / service / repository が同居）や同居テスト（`*.test.ts`）を範囲から外せない。

## Decision

- **コードに書く仕様外の印を廃止する。** `source.exempt_pattern`、`tests.exempt_pattern`、`tests.system.exempt_pattern` が設定に残っていれば、trace-check は設定エラー（exit 2）で止まり、移行先を案内する。
- **範囲はパスか glob の配列で宣言する。** `source.dirs`、`source.unit_dirs`、`source.support_dirs`、`tests.dirs`、`tests.system.dirs`、`schema.files` / `schema.dirs` は、パスか glob（`**` `*` `?`）の配列で、`!` で始まるものは除外、ファイルも書ける。テンプレートの `source.dirs` は `!**/*.test.*` `!**/*.spec.*` で同居テストを外す。
- **本番コードは 2 つの置き場に分ける。**
  - `source.unit_dirs`: 実現単位（ユースケースなど、仕様を実現する単位）の置き場。**C19** は、ここにあり `source.unit_pattern` に一致する単位がすべて窓に `@implements` を持つことを求める。例外は無い。
  - `source.support_dirs`（新設、必須）: REQ を持たない技術部品（外部境界のクライアント、設定の読み取り、値オブジェクト、エラー定義など）の置き場。`@implements` を求めないが、書いても違反にしない（UI やミドルウェアの分岐が REQ / BR を実現する正当な形）。
  - どちらも none にできるが、active な REQ がある間は none にできない（C26。ADR-0056）。
- **分類（C27）。** active な REQ がある間、`source.dirs` の全ファイル（`git ls-files -co --exclude-standard`。git が無ければドットで始まるものを除く全ファイル。拡張子を問わない）は `unit_dirs` か `support_dirs` のどちらかに入ること。どちらにも入らないファイルと、`unit_dirs` にあって拡張子が `source.extensions` に無いファイルを違反にし、ディレクトリ単位で 1 件にまとめて報告する。両方に入るファイルは設定エラー（exit 2）。
- **テスト**: `tests.dirs` は仕様のテストを置く場所の宣言そのもので、新しいキーは足さない。C11 は `tests.dirs` のテストがすべて `@covers` を持つことを求める。技術部品の自己検査は `tests.dirs` の外に置く（comments の規約、implementer の不変条件）。
- 仕様外を増やす経路は、`traceconfig.json` の場所の宣言を変えることだけになる。その変更は人間が承認する（ADR-0057）。テストの無い既存の単位は、特性テストを書くまで `support_dirs` に置く（docs-migrate）。
- 強制は trace-check（C11 / C19 / C27）で、develop の完了条件、stop-gate、CI を通じて効く。`support_dirs` に置かれたコードに業務ルールが紛れていないかは reviewer の確認で、説得による統制（R-901）。

## Consequences

- 良: 実装担当が 1 行で例外を作る経路が無くなる。新しいディレクトリやファイルを作っても、分類を宣言するまで違反になるので、範囲の外へ黙って出られない。
- 良: 例外の範囲は `traceconfig.json` の 1 か所に集まり、変更は差分と承認に現れる。reviewer が見る対象が `support_dirs` に絞られる。
- 良: 本番コードとテストで「仕様に紐づける範囲は場所で決まる」という同じ考え方になる。テンプレートの `layering`（domain / usecase / infra）とも揃う。
- 悪（破壊的変更）: `*.exempt_pattern` を設定している利用プロジェクトは、harness を上げると trace-check が設定エラーで止まる。印の付いた単位とテストを宣言の外へ移すか、REQ に紐づけてからキーを削除する。
- 悪: active な REQ を持つ利用プロジェクトは、`source.dirs` の全ファイルを分類する必要がある。画像や設定ファイルなど拡張子を問わないので、`source.dirs` を絞るか `support_dirs` に入れる。
- 悪: 技術部品のテストを `tests.dirs` の外に置くため、テストのディレクトリ構成を変える必要がある利用プロジェクトがある。`commands.test` がそのテストも実行するかは利用プロジェクトの設定に依存する。
- 悪: 業務ルールを `support_dirs` に置けば C19 を逃れられる。ただし置き場の追加は `traceconfig.json` の変更（人間の承認）で、既存の置き場に置くことは reviewer に残る。
- 悪: `unit_dirs` の中にも、REQ を持たない小さな補助関数を `export` することがある。`unit_pattern` を絞るか、補助関数を `support_dirs` に出す必要がある。

## 却下した選択肢

- **仕様外の印を残し、数をラチェットで増やさない**: 印の数を台帳で縛っても、印を書くのが作った本人である点は変わらない。台帳の更新がもう 1 つの例外の経路になる。
- **仕様外の印に ADR の参照を必須にする**: 技術部品ごとに ADR を書くのは重く、ADR が設計判断ではなく例外の届け出になる。
- **`unit_dirs` だけを宣言し、外は問わない**（最初の案）: 新しいディレクトリを作るだけで検査の外に出られる。外を `support_dirs` として宣言させ、どちらにも入らないファイルを違反にする。
- **`support_dirs` のファイルの `@implements` を違反にする**: UI コンポーネントやミドルウェアの分岐が REQ / BR を実現する正当な形を禁じ、注釈を消す誘因になる。
- **分類を走査対象の拡張子のファイルに限る**: 別の拡張子のファイルに単位を置けば C19 を逃れられる。
- **分類の違反をファイルごとに報告する**: 既存のディレクトリ 1 つで数百件になり、直し方（置き場を 1 行宣言する）が見えなくなる。
- **テスト側にも `tests.unit_dirs` などのキーを足す**: `tests.dirs` がすでに「仕様のテストを置く場所」の宣言になっている。キーを増やすと、同じ意味の宣言が 2 つになる。
- **すべての本番コードに `@implements` を求める**: REQ を持たない技術部品（ADR-0051）が違反になる。REQ は外から観測できる振る舞いだけを持つ（R-401）ので、技術部品のために REQ を作ることもできない。
