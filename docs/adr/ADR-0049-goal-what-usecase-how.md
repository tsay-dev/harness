# ADR-0049 GOAL は達成状態の What、UC は達成手段の How と定義する

## Context

利用者から、AI が GOAL に達成手段を書いてしまうため、GOAL を目指す状態（What）、UC をそこへ至る手段（How）として定義するよう依頼された。既存の規約は GOAL を「actor の言葉による 1 文」、テンプレートは「〜したい」としており、望む状態と操作への希望を区別していなかった。UC には観測可能なシナリオと事後条件があったが、GOAL との意味的な関係は明記されていなかった。

## Decision

`docs.instructions.md` の R-301 / R-302 を意味の定義の正本とする。GOAL はアクターが目指す達成後の状態・成果であり、手段を替えても同じ状態を指す。UC はその状態へ至る利用・業務上のやり取りを表す。UC の成功時の事後条件には GOAL への寄与を示すが、一つの UC に GOAL 全体の達成を要求しない。UC の How に技術選定、アルゴリズム、画面構造などの実装設計は含めない。

GOAL と backlog の記入欄、UC の概要と事後条件をこの定義に合わせる。spec-author は手段しか分からない入力から目的を創作せず、不足を返す。reviewer は参照先 GOAL も受け取り、達成状態と手段の混同、UC の成功時事後条件の不整合を検査する。定義の適用はテンプレート・指示・レビューによる説得的統制である（R-901）。spec-lint と trace-check は書式と参照を検査し、What / How の意味的な正しさを証明しない。

## Consequences

- 良: GOAL が操作名や機能名に置き換わる余地を減らし、同じ目標へ至る複数の UC を扱える。backlog の段階から同じ意味を保てる。
- 良: 書式、ID、ステータス、配置は変えず、既存の検査と人間承認の仕組みを維持できる。
- 悪: 状態と手段の区別は文脈に依存し、機械検査だけでは保証できない。情報不足の入力では達成したい状態の確認が必要になる。
- 悪: 既存の消費プロジェクトの GOAL は自動修正されない。更新したパッケージとテンプレートを取り込み、手段が混在する既存文書は人間承認を経て見直す必要がある。

## 却下した選択肢

- **「〜したい」という書式だけを維持する**: 操作への希望も同じ形で書けるため、今回の混同を防げない。
- **UC の How に実装設計も含める**: 観測可能な利用シナリオと内部設計が混ざり、実装手段を替えるたびに仕様が変わってしまう。
- **語尾や操作語の正規表現で GOAL を拒否する**: 同じ語でも文脈によって状態や手段になり、意味を検査できたという誤った保証になる。
